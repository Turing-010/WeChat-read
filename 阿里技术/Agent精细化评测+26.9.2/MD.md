回顾 NLP 领域的评测历史，BLEU、ROUGE 等指标曾是机器翻译和⽂本摘要的标准评测⼿段。

2.2 为什么要拆到模块级别去评测？
假设 Agent 任务完成率从 85% 掉到了 60%，原因可能是：
感知模块把“查 Trace”错误识别为知识库问答（意图识别错误）
规划模块在应该调⽤ Skills 时选择了 RAG 检索（路由决策错误）
记忆模块在多轮对话中丢失了上⼀轮提到的商品 ID（记忆丢失错误）
⼯具模块错误调⽤了 MCP 或⼯具参数填充错误（⼯具调⽤错误）
端到端评测本质上是⼀个⿊盒测试，就像是把⻋开上测试跑道：它不关⼼发动机转速、变速箱换
挡逻辑或刹⻋⽚磨损程度，只回答⼀个⽤户视⻆的问题——这辆⻋能不能从 A 地开到 B 地。模
块级评测则是⽩盒诊断：把⻋架上升降台，看发动机、刹⻋、油路各⾃的状态，关⼼⻋辆能不能
安全、准时、经济地抵达⽬的地。端到端评测定义了“好⻋”的标准，模块级评测提供了“把⻋修
好”的路径，两者应该相辅相成。
2.3 为什么需要“质量 × 成本 × 性能”指标？
⼀个“回答正确但耗时 30 秒”的 Agent 不是好 Agent；⼀个“回答正确但每次消耗 10 万
Token”的 Agent 不可持续。Agent 最终要部署到⽣产环境服务真实⽤户，评测框架必须同时回
答三个问题：答案好不好？成本⾼不⾼？速度快不快？
因此，本⽂将 AI Agent 应⽤评测设计为三个维度：
质量维度：答案是否正确、完整、忠实于知识来源，是否出现幻觉。这是底线，但不是全部。
成本维度：每次请求触发了⼏次模型调⽤、调⽤了⼏轮外部⼯具、消耗了多少 Token。
性能维度：从⽤户按下回⻋到看到第⼀个字的时延，以及到完整回答结束的时延，直接决定了
⽤户体验。
这三个维度理论上缺⼀不可，只追求质量，可能在成本和延迟上失控；只优化速度，可能在复杂
问题上过于简化；只看成本，可能导致准确率断崖式下跌。健康的 Agent 应是三个维度在当前业
务场景下的最优平衡。
2.4 评测范围、数据集与指标的映射
参考已有评测⼯作，本⽂将整体评测分为两个部分：
端到端评测：主要关注 Agent 在接收到单⼀⽤户问题后，能否⾃主、有效地完成整个任务流程，
并达到预期的输出效果，从任务完成质量、任务成本消耗、任务完成效率和安全鲁棒性四个维度
综合衡量 Agent 的整体表现。
核⼼模块评测：主要关注核⼼模块的评测（感知、规划、记忆、⼯具），⽤于深⼊分析Agent的内
部⼯作机制和潜在瓶颈。每个模块从能⼒、效率和有效性等多个评测维度进⾏细粒度评估，帮助
定位具体问题根因。

5.2 Judge Prompt 的设计原则
好的 Judge Prompt 是评测质量的基础，结合实践经验，本⽂总结了四条设计原则：
第⼀，单⼀职责。 ⼀个 Prompt 只评测⼀个指标。之前尝试过在⼀个 Prompt 中同时判断任务完
成率和忠实性，结果两项指标的准确率都下降了。原因很简单：多任务混合会增加 LLM 的理解负
