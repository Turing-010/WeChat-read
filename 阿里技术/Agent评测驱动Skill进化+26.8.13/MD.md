```text
更棘⼿的是，这件事没法「⼀次性写对」。⼀个 agent 要⾯对的任务千变万化，我们不可能预先
就把 skill 写到完美，只能在实战⾥⼀个个 case 地暴露短板，再⼀版版地补。⼈⼯盯着这个过
程，既慢，⼜容易顾此失彼。
因此，我想做的是把「改 skill」这件事变成⼀套可重复的流程，让 agent 完成任务的能⼒，沿
着评测结果⾃⼰往前⾛。
拆开来看，这套流程⼤概分为五个步骤：
1. 跑⼀批测试任务，看 agent 在哪些 case 上做错了；
2. ⾃动分析它为什么做错（不是瞎猜，是有规则的）；
3. ⾃动⽣成⼀个 patch 去改它的 skill（SKILL.md）；
4. 改完之后再验证——确保改好了这个，没搞坏那个；
5. 如果验证通过，就接受这次修改；不通过，就丢掉，记到⿊名单⾥。
跑过⼏轮之后，agent 处理这类任务的能⼒就会慢慢变得稳定。
这⾥⽐较容易被误解的⼀点是，这其实不是「让 AI ⾃⼰教⾃⼰」，LLM 只负责把诊断结果写
成候选修改；诊断、验证、回滚、⿊名单这些容易出事故的环节，都交给可复查的规则。
我不假设模型会突然变聪明，只是把它容易“犯糊涂”的地⽅收进⼯程约束⾥。
什么任务适合这么⼲
先说清楚，不是所有 agent 任务都能这么玩，能不能跑⾃进化，只取决于⼀条标准：这个任务的
输出，能不能被客观判定对错。
判据就这⼀条，但它筛掉了⼀⼤半任务。能通过的任务有个共同点：结论是收敛的、有标准答案
可对照的。是不是垃圾邮件、这段代码有没有漏洞、从合同⾥抽出的⾦额对不对......对就是对，
错就是错。相反，「写⼀段⽂案」「把这篇⽂章总结得漂亮点」这类开放式任务就不⾏：好坏⻅
仁⻅智，没有唯⼀标准答案，若是连「这次改得好不好」都没法机械判断，⾃然谈不上让它⾃动
迭代。
```

04
第⼀个反直觉设计：诊断不⽤ LLM
这是整套系统最反直觉的⼀个决定。诊断阶段完全不⽤ LLM，只⽤确定性规则。
有⼈可能会问：既然都是 AI 的事，为什么不让 AI ⾃⼰判断哪⾥错了？
答案来⾃⼀次不太好看的实验结果，让 LLM 直接判断 skill 好不好，稳定性明显低于规则⽅法，
部分设置接近随机⽔平。
这⾥的「测过」不是拍脑袋。我们抽取了历史失败 case 的 session 摘要和⼈⼯复盘结论，让
LLM 判断「是不是 skill 流程问题、该不该改 skill」，再跟⼈⼯归因和规则诊断结果对照。结果
很不稳定，同⼀批 case 换⼀次 prompt 或模型温度，结论就会明显漂移；⽽规则诊断虽然覆盖
⾯有限，但⾄少不会因为 prompt 或采样参数变化⽽漂移。最后我们接受了⼀个更朴素的取舍：
诊断宁可少判，也不要飘着判。
想想也合理，让员⼯⾃⼰评判⾃⼰的⼿册写得好不好，能有多客观？

```text
诊断引擎怎么⼯作：三层压缩 + 可扩展规则
诊断分两步，先压缩，再判断。
第⼀步：trace_parser——把 agent 的「答题过程」压缩 100 倍。
原始 session ⽂件可能有 10-50 万 token（⼀次审计 agent 可能读了⼏⼗个⽂件、调了上百次
⼯具），如果直接喂给 LLM 会超窗⼝、注意⼒稀释、结果不可复现。
trace_parser 把这些信息压成三层：
1 层 1: ⼯具调⽤⻣架（保留⼯具名 + 参数摘要，丢弃返回内容）
2 层 2: 阶段统计（每类⼯具调了⼏次、error ⼏个、重试⼏次）
3 层 3: 进度交叉验证（Agent 声称执⾏了 STEP1/2/3，实际 session 有没有对应调⽤）
压缩⽐约 100:1。⼏⼗万 token 的原始 session，压成⼏千 token 的结构化 JSON。
trace_parser 还能⾃动识别两种不同的 session 格式——标准 JSONL 和 Claude Code 原⽣
transcript 格式，通过扫描前⼏⾏的特征⾃动路由，⽤户不需要⼿动指定。
第⼆步：flow_diagnosis——⼀组可扩展的规则。
当前内置了⼀组基础规则，每条规则检测⼀种「agent ⼲活时的坏习惯」：
规则 检测什么 ⽤⼈话说
no_tool_calls session ⾥零⼯具调⽤ 不⼲活
redundant_retry 同⼀个⼯具、同样参数调了 ≥3 次 反复做同⼀件事，没有进展
repeated_file_edits 同⼀⽂件被编辑 ≥5 次 试错型修改
tool_error_burst 真实 error ≥8 条（排除搜索空结果） 连续出错
tool_error_high_rate 单⼯具 error 率 ≥50% 某个⼯具基本⽤不好
```
