整体架构：数仓+推理平台串联
我们没有把所有逻辑都塞进推理 workflow，⽽是按"数据归数据、推理归推理"的原则做了
明确分⼯：推理平台只负责 LLM 推理任务（拼接 Prompt → 调⽤模型 → 返回结构化结
果），前期的数据清洗、多源拼接、过滤规则，以及后期的结果解析、标签归⼀化、指标聚
合，全部在数仓 SQL 中完成。这样做的好处是：
推理平台保持轻量，不承载业务逻辑
数据预处理和后处理都在数仓中⽤ SQL 实现，可复⽤、可回溯、可独⽴调试
两端解耦后，改 Prompt 不需要改数据逻辑，改过滤规则不需要重跑推理，迭代效
率更⾼。
数据完整性校验：Check 节点
在推理完成后，设置了 check 节点：对⽐ input 表的条数与推理输出的 output 表条数，
只有两者⼀致才进⼊下⼀步的结果解析。这是因为我们在使⽤过程中发现：
公共推理资源池⾼峰期偶发推理超时导致部分数据丢失
回刷同分区数据时，结果表是叠加⽽⾮覆盖分区
如果没有 check 节点，下游直接计算会导致通过率算错。
⼯作流设计：按域拆分独⽴ Workflow

短板效应：最慢的域拖住所有域；
故障扩散：单域失败阻塞整个workflow；
迭代耦合：改某域的 Prompt 需要重跑所有域。
最终采⽤各域独⽴ workflow 的⽅案，每个 workflow 独⽴配置队列、并发度和重试策略。
规模实测（示意）

Prompt 设计再好也⽆法 100% 杜绝⾮标输出。因此解析侧还有三层兜底：
Prompt 约束：强制模型输出结构化格式（各维度严格输出 0/1/剔除）。

标签归⼀化：对评分字段做归⼀化处理（新旧格式混合、输出空值/⾮标准值的分级
CASE WHEN 处理）。
踩坑：数仓正则提取函数存在转义陷阱，SQL 中的反斜杠会被逐层解析，导致⻓⽂本提取的
正则表达式需要反复调试才能稳定⼯作。

个问题的难点在于：我们不知道"真实的线上⽔位"是多少，没有⼀个 ground truth 可以对
照。离线评测的通过率不能直接搬到线上（数据形态不同），⼈⼯抽检的通过率样本量有限
