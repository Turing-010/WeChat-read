# 重构一个类，JVM竟省下2.9G内存？

## 1. TL;DR

1. **核心痛点**：在十万级商品 $\times$ 万级城市 $\times$ 多条件树状动态过滤场景下，应用层本地缓存（3 分钟 TTL）的响应类 `RecallPlatformTagsResp` 采用嵌套通用集合 `Map<Long, Set<String>> resultMap` 存储商品标签，在生产高并发缓存下单个结构竟吞噬高达 **3,205MB（≈3.13GB）** JVM 堆内存。
2. **数据分布洞察与双重重构方案**：统计 100 万商品样本发现，所有标签 ID 均为 **`< 5000` 的正整数**，且标签数量高度右偏（**80% $\le 16$ 个、90% $\le 32$ 个、99% $\le 64$ 个、100% $< 128$ 个**）且初始化后只读不变；据此执行“双重手术”：
   - **Value 层（贡献主要收益）**：用**排序后的原始类型数组 `int[]` + 二分查找**替代 `HashSet<String>`（在 10 万样本实测中仅此一步即从 `1.3GB` 降至 `64MB`），90% 查询仅需 **5–6 次**比较（最多 **7 次**），连续内存对 CPU 缓存极度友好；
   - **Key 与 Map 容器层**：引入工业级高性能集合库 **FastUtil** 的 `Long2ObjectOpenHashMap<int[]>` 替代 `HashMap<Long, ...>`（10 万样本实测进一步从 `64MB` 压至 `25MB`），基于两个平行数组（`long[] key` + `Object[] value`）与开放寻址线性探测彻底消除 `Long` 装箱与 `Map.Entry` 节点开销。
3. **生产双写验证战果**：线上通过新老结构并行双写对比验证后切换，JVM 堆内存从 **3,205MB 直降至 211MB**，净省 **2,994MB（≈2.9GB）**，新结构内存占用仅为老方案的 **6.5%（降幅达 94% 以上）**。

## 2. 问题定义与背景

### 2.1 为什么必须在应用层缓存全量商品标签？

业务核心接口需按城市维度对商品标签执行复杂的动态过滤（支持多条件 AND/OR 嵌套、多层级树状表达式及运行时上下文计算），无法用搜索引擎原生 DSL 或简单脚本预编译表达，因此必须将全量商品标签加载至 JVM 内存并设置 **3 分钟 TTL 本地缓存**跨请求复用。

### 2.2 老结构 `Map<Long, Set<String>>` 的三重“隐形内存黑洞”

在 `RecallPlatformTagsResp` 中，原始定义为 `private Map<Long, Set<String>> resultMap;`（例如 `{1: ["2246", "2288", "3388", "1022"]}`）：
1. **类型错配与未池化字符串浪费**：业务上所有标签 ID 都是 **小于 5,000 的正整数**，老代码却为所谓的“扩展性”存成未放入字符串常量池（未 `intern`）的 `String` 对象，每个标签都背负 `String` 对象头、字符数组引用、哈希值等沉重开销。
2. **`HashSet` 底层 `HashMap` 嵌套膨胀**：每个商品都持有一个独立的 `HashSet<String>` 实例（底层即一个 `HashMap`），包含桶数组、`HashMap$Node` 链表节点对象头、前后指针与扩容空闲槽位。
3. **外层 `HashMap<Long, ...>` 装箱与节点开销**：百万级商品 `shid` 触发百万个 `Long` 包装类实例与外层 `Node` 节点对象。

### 2.3 决定技术选型的 100 万商品标签分布统计

对约 **100 万个 `itemId`** 的真实标签分布统计显示：
- **80%** 的商品标签数 **$\le 16$**
- **90%** 的商品标签数 **$\le 32$**
- **99%** 的商品标签数 **$\le 64$**
- **最大标签数 $< 128$**（绝对上限明确、高度右偏）

这直接推导出：**在小规模（$k \le 128$）、只读静态、稠密小整数场景下，无需动态扩容与运行时去重的 `HashSet`，排序后的紧凑 `int[]` + 二分查找就是最优解。**

## 4. 核心内容拆解

### 4.1 为什么排序 `int[]` + 二分查找能完胜 `HashSet<String>`？

1. **去重冗余**：商品标签在初始化入库时已由上游保证唯一性，运行时根本不需要 `HashSet` 的动态去重能力。
2. **空间与 CPU 缓存局部性压倒性优势**：
   - `int[]` 仅需 **$4k$ 字节**（$k$ 为标签数）加一个数组对象头，无任何 `Entry` 节点与指针开销；
   - 数组在物理内存中连续排列，CPU L1/L2 Cache 预取（Prefetch）命中率极高。
3. **时间复杂度 $O(\log k)$ 与 $O(1)$ 在 $k < 128$ 下无体感差异**：
   - 80% 商品（$k \le 16$）最多比较 **4 次**；
   - 90% 商品（$k \le 32$）最多比较 **5 次**；
   - 极端最大商品（$k < 128$）最多比较 **7 次**；且彻底消除了哈希碰撞退化风险。

### 4.2 多方案 JProfiler 实测对比（`MemoryComparisonTest2`）

作者构造了模拟真实分布（总标签池 `3,000` 个，标签值 `1000~10000`，90% 商品 `1~16` 个标签、10% 商品 `17~100` 个标签）的基准测试，并用 JProfiler Dump 堆内存横向对比了 6 种结构：
1. `Map<Long, Set<String>>`（未池化，原线上结构）：测试集占用 **`1.3GB`**；
2. `Map<Long, Set<String>>`（使用 `String.intern()` 常量池去重）；
3. `Long2ObjectMap<BitSet>`；
4. `Long2ObjectOpenHashMap<RoaringBitmap>`；
5. `Map<Long, int[]>`（仅改 Value 为 `int[]`，外层仍用 JDK `HashMap`）：内存从 **`1.3GB` 骤降至 `64MB`**（证明 **Value 层精简贡献了最大头收益**）；
6. `Long2ObjectOpenHashMap<int[]>`（FastUtil + `int[]` 双重优化）：内存进一步从 **`64MB` 压缩至 `25MB`**！

### 4.3 `Long2ObjectOpenHashMap` 底层原理深度剖析

`FastUtil` 自 2000 年代初持续维护，被 **Apache Spark、Elasticsearch、Neo4j、Deeplearning4j** 等工业级系统广泛采用。其核心机制如下：
1. **平行数组 + 开放寻址法（Open Addressing）**：
   - 内部不存 `Node` 链表或红黑树，仅维护两个平行一维数组：`long[] key` 与 `Object[] value`；
   - 容量保持为 2 的幂，`mask = array.length - 1`。
2. **64 位 `long` 哈希扰动与位与取模**：
   - 摒弃慢速且有负数隐患的 `% capacity` 运算，采用高低 32 位异或扰动：
     ```java
     int hash = (int)(key ^ (key >>> 32));
     int index = hash & mask;
     ```
3. **线性探测（Linear Probing）冲突解决与查找终止条件**：
   - **插入（`put`）**：若 `key[index] != 0`（如容量为 8、`mask = 7` 时连续插入 `1000`、`1008`、`2000` 均映射到 `index = 0`），则依次向后探测 `(index + 1) & mask` 直至找到空槽 `key[i] == 0` 填入（最终分别落在下标 `0, 1, 2`）。
   - **查找（`get`）**：从 `hash & mask` 开始沿探测链向后比对，直到找到匹配的 `key` 返回 `value[i]`，或**遇到空槽 `key[i] == 0` 立即终止查找返回不存在**。
4. **为什么 `remove()` 删除元素时绝不能直接把 `key[i]` 置为 `0`？（后向位移算法 Backward Shift）**：
   - **直接置 0 的灾难**：在上述 `[1000, 1008, 2000, 0, ...]` 例子中，若 `remove(1000)` 直接令 `key[0] = 0L`，后续调用 `get(2000)` 时在起始位置 `index = 0` 看到空槽 `0L` 就会**立即终止查找**，导致原本存在的 `1008` 和 `2000` 永远失联！
   - **后向位移（Backward Shift）三步正确解法**：
     1. 将被删位置标记为临时墓碑 `key[0] = REMOVED_KEY`（`-1L`）；
     2. 向后扫描探测链上的元素（如位置 1 的 `1008` 和位置 2 的 `2000`），计算其理论哈希槽位（均为 `0`），发现前方存在空洞后依次将 `1008` 前移至位置 `0`、`2000` 前移至位置 `1`；
     3. 扫描到位置 3 遇到真正的空槽 `0L` 时停止位移，并将最后一个临时墓碑（位置 `2`）清理为 `EMPTY_KEY (0L)`，最终数组紧缩为 `[1008, 2000, 0, 0, ...]`，既不截断探测链，又不像持久化墓碑那样堆积垃圾槽位。
5. **使用边界与三大避坑指南**：
   - 当**负载因子 `> 0.7`** 时线性探测冲突加剧、性能急剧下降，初始化时务必预估容量（如预估 `10,000` 个元素时传入 `16384`）；
   - 避免 Key 全部为 $2^k$（如 8）的整数倍导致严重哈希聚集；
   - 非线程安全，不适用高频并发写场景，极适合“构建后只读或单线程/外部同步缓存”的高频 `long -> Object` 映射。

## 7. 记忆锚点

1. **双重瘦身阶梯公式**：$\text{HashMap<Long, Set<String>>（3.2GB / 测试 1.3GB）} \xrightarrow{\text{Value 改排序 int[]}} \text{64MB} \xrightarrow{\text{Map 改 Long2ObjectOpenHashMap}} \text{25MB（生产 211MB，省 94\%+）}$。
2. **FastUtil 核心三机制**：“**平行数组消装箱（`long[] + Object[]`）、高32异或位与模（`key ^ (key >>> 32)`）、删除后移防断链（`Backward Shift`）**”。

## 8. 复习卡片

1. 为什么 `RecallPlatformTagsResp` 中的 `Map<Long, Set<String>>` 在百万商品规模下会消耗高達 3.2GB 的 JVM 堆内存？::由三层开销叠加导致：① 标签明明都是小于 5,000 的正整数，却用未去重的 `String` 存储；② 每个商品都创建一个独立的 `HashSet`（底层即 `HashMap`，含桶数组与 `Node` 对象头/指针）；③ 外层 `HashMap` 产生百万个 `Long` 自动装箱对象与 `Node` 节点。
2. 基于 100 万商品样本的统计，商品标签数量呈现怎样的分布特征？为什么由此能用 `int[]` + 二分查找替代 `HashSet`？::统计显示 80% 商品标签数 $\le 16$、90% $\le 32$、99% $\le 64$、最大 $< 128$，且数据只读、上游已保证唯一性；在此规模下有序 `int[]` 仅占 $4k$ 字节且连续内存对 CPU Cache 极友好，二分查找对 90% 商品仅需 $\le 5$ 次比较（最多 7 次），延迟与 $O(1)$ 几乎无感差异却省下 94%+ 内存。
3. 在“将 `Set<String>` 改为 `int[]`”与“将 `HashMap` 改为 `Long2ObjectOpenHashMap`”这两项改动中，哪一项贡献了主要的内存下降收益？实测数据是多少？::Value 层（将 `Set<String>` 改为 `int[]`）贡献了最大头收益：在 10 万商品测试集中，仅将 Value 改为 `int[]`（外层仍用普通 `HashMap`）内存就从 `1.3GB` 骤降至 `64MB`；再将外层换为 `Long2ObjectOpenHashMap<int[]>` 后进一步压至 `25MB`（线上总堆内存从 `3,205MB` 降至 `211MB`）。
4. FastUtil 的 `Long2ObjectOpenHashMap` 底层使用什么数据结构存储键值对？它是如何计算 `long` 类型 Key 的数组下标的？::底层摒弃链表/红黑树，使用 `long[] key` 和 `Object[] value` 两个平行一维扁平数组配合开放寻址（线性探测）；索引计算通过 `int hash = (int)(key ^ (key >>> 32)); int index = hash & mask;`（混合高低 32 位后与 `capacity - 1` 按位与）完成。
5. 为什么在 `Long2ObjectOpenHashMap` 中执行 `remove(key)` 时，不能直接把对应的 `key[index]` 置为 `0L`？它是如何正确处理的？::因为 `get()` 查找依赖“遇到空槽 `0L` 立即终止”；若直接置 `0L` 会截断线性探测链，导致后续因哈希冲突向后顺延存放的元素永远查不到。正确做法是采用“临时墓碑（`-1L`）+ 后向位移（Backward Shift）”，将后续需要前移的冲突元素依次向前紧缩填补空洞，直到遇到真正的空槽 `0L` 再清掉尾部墓碑。
6. 使用 `Long2ObjectOpenHashMap` 时有哪些性能红线与不适用场景？::当负载因子 `> 0.7` 时线性探测冲突会急剧拉低性能，因此初始化时应预估容量（如 10,000 元素配 `16384`）；不适用于高频并发写（非线程安全）、Key 分布极不均匀（如全为 8 的倍数导致同槽聚集）的场景。
