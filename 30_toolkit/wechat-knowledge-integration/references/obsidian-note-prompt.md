<目标>

把我上传或归档在知识库中的课件、PPT、PDF、讲义、逐页转写（`MD.md`）、文章或技术报告，转成一份可直接放进 Obsidian 与本地知识库的技术精读学习笔记，交付单个 `.md` 文件，用于深度理解、间隔复习和日后引用。

默认读者：有 RAG / LangGraph / 分布式系统与大模型工程经验的工程师；我另行指定背景时，以指定内容为准。基础概念一笔带过，重点写方法、机制、设计取舍、工程细节和易错点，不在笔记开头反复解释读者假设。

笔记应是「有讲解的结构化学习材料」，不是极简摘要、原文目录翻版或纯速查表：读完能说清它解决什么问题、为什么这样设计、具体怎样运转、什么条件下成立。

若同时提供风格范例，学习其组织方式和讲解深度；除非我明确要求综合这些资料，否则不把范例中的技术事实带入本次笔记。

</目标>

<工作流程>

1. 通读材料（`MD.md` 逐页转写文本与 `RAW.pdf` 原页），检查正文、图表、截图、代码、脚注与附录，确认哪些内容实际可读；解析文本没有显示图表或公式时，查看对应页面图像，不把提取失败当成原图缺失。
2. 判断主类型：技术精读 / 工具操作型 / 概念理论型 / 方法论与案例型 / 论文型；允许混合类型，按内容组织拆解深度，不因归入方法论型就删掉操作步骤、配置或实验设置。
3. 建立内部「事实与来源清单」：记录数字、单位、阈值、公式、术语、代码、命令、字段、图中节点与关系，以及各自的原文物理页码位置（`p.X`）和适用语境；推断另记依据，不与原文事实混放。
4. 识别原文主线和主要章节，保留作者自己的分层、阶段、方案演进和问题分类；可以优化重组阅读顺序，但不把原文没有的因果关系或系统架构补进去。
5. 按下列 10 节标准结构生成笔记，再对照原文和清单校对，尤其检查摘要、图表、数据速查表、记忆锚点、复习卡片之间是否一致，并确保**正文零内联页码**（所有页码溯源统一放入文末折叠的 `> [!note]- 校对报告`）。

事实清单用于核对，不单独交付；不要输出分析过程，用文末折叠校对报告体现页码溯源与核验结果。

</工作流程>

<写作方式>

### 讲清机制，不只压缩结论

- 每个核心小节先给一句主张，再根据原文讲清「遇到什么问题 → 采用什么机制 → 为什么有效 → 有什么代价或边界」；原文没有的环节不补写。
- 「一个要点一句话」改为「一个要点只讲一个意思」：允许用必要的几句话解释机制和条件，不为压缩篇幅省掉因果、前提、例外和失败分支。
- 保留能帮助理解的原文案例、反例、形象表达和关键实现细节；基础背景可压缩，方法细节不能只剩口号。
- 重要术语首次出现时给出原文支持的定义或用途，不依靠读者自行展开缩写；原文未定义的术语保留原词，不凭常识补全。

### 用结构帮助理解，而不是堆表格

- 概念边界、角色职责、方案取舍、配置关系适合表格；因果、演进过程、案例推演适合分点或短段落；操作规程适合步骤或代码块。
- 对比要回答实际判断问题，例如「各自负责什么」「为什么不能互相替代」「何时选哪种方案」「改善了什么又牺牲了什么」，比较维度须由原文支撑。
- 几组不同的概念对照可以分成小表，不塞进一张横向过宽的大表；不要把整篇正文改造成速查表。
- 表格字段按材料调整，不为填满「适用场景 / 局限」编造信息；整列缺乏依据时删除该列，个别必要单元格缺信息时写「原文未说明」。

### 保留工程细节，控制无效重复

- 对核心方法保留原文给出的输入、输出、阶段、分支、约束、验证、停止与恢复条件；对架构保留组件职责、交接产物、关键字段及依赖关系。
- 原文提供完整 Prompt、操作规程或配置示例时，优先完整保留有复用价值的示例，并解释关键约束，不只拆成零散参数；同一示例只完整出现一次。
- 篇幅由原文的信息量决定，不设固定压缩比：短材料不扩写，长材料不强行压成短摘要；主要章节和关键机制应有实质覆盖。
- 正文负责讲透，数据表负责查数，踩坑负责提醒，卡片负责自测；允许不同用途的短回顾，不在多个模块重复整段解释。

</写作方式>

<模块>

全文严格采用 **1 个一级标题（`# 标题`） + 10 个编号二级章节（`## 1.` 至 `## 10.`） + 底部折叠校对报告（`> [!note]- 校对报告`）** 的标准结构：

### `## 1. TL;DR`

用 3–5 句（或结构化总览要点）概括核心痛点、核心方法与关键机制，以及原文提供的核心量化结果或重要边界；优先让人一眼看懂全文技术主张与工程收益。

### `## 2. 问题定义与背景`（或 `## 2. 核心概念`）

清晰界定本文要解决的核心工程/算法痛点、为什么传统方案失效、以及必要的前置概念定义与边界对比；保留原文语境，区分作者的专门用法与一般概念。

### `## 3. 知识框架`

必须使用一张 `mermaid`（`flowchart` 或 `mindmap`）展示全文主线、模块分工、数据流或方法层次。

关键子流程、状态变化或架构可以另画 Mermaid，放在第 4 节对应小节附近，并配文字说明。

### `## 4. 核心内容拆解`（或 `## 4. 关键要点与机制详解`）

这是正文主体，采用 `### 4.1 ...`、`### 4.2 ...` 分层拆解，优先沿用原文有辨识度的主题、分层和方法名称作为小节标题。

重点保留：问题如何被重新定义、方案为何演进、组件怎样配合、判定如何分流、失败怎样处理、效果如何验证；相关案例、数学公式和具体配置字段跟随对应机制讲解。

| 材料内容 | 应保留的内容 |
|---|---|
| 工具操作 | 命令速查（命令｜作用｜场景）、前置条件、分步操作、配置及注释、输入输出示例、常见坑；决定成败的步骤可标 🔥。 |
| 概念理论 | 问题边界、原文定义、概念关系、关键命题、公式及符号、成立条件、原文例子与反例。 |
| 方法论与案例 | 原文方案对比、选择依据、演进动机、实施机制、案例结果、局限与可迁移原则。 |
| 论文或技术报告 | 问题、方法、实验设置、对照与消融、结果、结论和局限；明确哪些已验证、哪些只是作者设想。 |

### `## 5. 数据速查表`

使用三列表格 `| 指标 | 原文数值 | 语境 / 条件 |` 汇总全文关键量化数据、超参数、硬件规格、耗时与对比基准（若全文主要为配置项或架构对比，表头可调整为 `| 指标 / 配置项 | 原文数值 / 表达式 | 语境 / 条件 |`）。

优先保留效果、样本量、阈值、预算、时间、版本和对照结果；不同实验、版本、阶段、样本或时间窗口在「语境 / 条件」列明确区分，不拼成一条原文没有的提升路径；示例参数注明为示例，不写成通用默认值。不在表内单独设页码列，页码出处统一归入文末 `> [!note]- 校对报告`。

### `## 6. 踩坑与教训 / 可迁移的设计原则`

使用三列表格 `| 错误做法 | 失败表现或原因 | 原文应对（可迁移的设计原则） |` 提炼工程避坑指南与可复用的架构设计原则。

设计原则保留适用条件；作者明确提出的原则可以直接概括，超出原场景的推广标 `[推断]` 并说明依据，不把单个案例写成普遍规律。

### `## 7. 记忆锚点`

保留 1–2 个能串起核心机制与关键数字的高辨识度口诀、对照公式或核心金句。不能为了顺口改动时间、数字、条件或因果关系。

### `## 8. 复习卡片`

生成 **5–8 条（最多不超过 10 条）**，严格使用 `问题::答案` 格式，每条单独占一行（中间不换行）。

优先问机制原理、方案区别、选择条件、失败原因和关键约束，不只问名词展开或孤立数字；每条只考一个核心知识点，答案尽量用 1–3 句说完整。答案必须在正文中找到依据；重要条件不能在卡片中被省掉。

### `## 9. 知识关联`

- **本库通用主题**：当在本地知识库中生成笔记时，必须包含指向 `../../20_topics/xxx.md` 的真实有效相对路径链接（可从文章 `META.json` 或现有笔记继承并核验可达性）。
- **候选双链**：给出 3–5 个细粒度候选 `[[双链]]`，方便后续在 Obsidian 中拓展知识图谱。

### `## 10. 原文参考资料`

列出原文完整标题、作者/团队、发布日期，以及原文中明确提供的开源仓库地址、论文链接或技术参考文档（注明来自原文，不声称已联网访问核验；纯营销抽奖推广入口不保留）。

</模块>

<准确性规则>

### 来源边界

- 无标记 = 有原文直接支持的转述；可以重组表达，不能改变含义、范围、确定性或因果强度。
- `[推断]` = 原文未明说、但能由明确证据推导出的结论，标在具体句子或图中关系旁，并指出依据；不能用它包装猜测、补齐缺失内容或低置信读图。
- `[扩展]` = 外部知识，仅在确有必要时标注并提供可核验来源；默认不主动补充外部未核实信息。
- 作者判断写成「作者认为 / 本文主张」，案例结果保留实验条件，未验证规划保留其设想身份；不把观点写成已证实事实，不把局部结果写成普遍保证。

### 数字、公式与实现细节

- 数字、阈值、单位、比较符号、范围、默认 / 可选属性、版本、字段、命令和路径以原文为准；不要改写或省略影响含义的部分。
- 原文公式完整保留，符号定义仅采用原文说明；不得根据熟悉的算法补公式或默认参数。
- 摘要、正文、表格、图、锚点和卡片必须共用同一事实口径，尤其检查时间先后、对象归属、指标分母和前置条件。

### 疑点与缺失

- 文字或数字放大后仍无法辨认，在文末校对报告或必要处注明无法辨认或文本层缺失，不猜读补造。
- 确认原文存在内部数值冲突、编号跳号、错引或代码右侧裁切时，切勿静默篡改或自行补造被截断的 URL/代码；可在第 6 节或文末 `> [!note]- 校对报告` 的「勘误与内部矛盾说明 / 核验记录」中明确指出。

</准确性规则>

<图表与代码>

### 图表

- 含架构图、流程图或状态图时，用文字 + Mermaid 保留关键结构。
- 核对节点、包含关系、箭头方向、边标签、分支和回路；不能把并列组件改成串行步骤，不能把时间顺序误写成数据流。
- 数据图表优先转为可核对的表格或文字趋势说明，并保留原图所表达的对照和条件；不能从无数字示意图估算精确数值。

### 代码、命令与 Prompt

- 保留原文命名、参数、顺序、注释、占位符和关键上下文；能确认的排版断行可以恢复，不能静默修复逻辑或补造接口。
- 完整示例按对应语言标注代码块；若正文外展示含 `#` 注释的 Shell/Python 代码，必须包裹在代码块内，确保代码块外全篇仅有 1 个一级标题 `# 标题`。
- 被截断或无法辨认的代码不为了看起来完整而猜测补全，并在校对报告中说明。

</图表与代码>

<来源标注与正文零内联页码规则>

- **正文零内联页码（硬性门禁）**：在文末 `> [!note]- 校对报告` 之前的正文、各级标题、表格、图注和复习卡片中，**一律不得出现 `p.X`、`p.X–Y` 或 `第X页` 等内联页码标记**，确保笔记正文阅读流畅。
- **页码溯源集中归档**：全文所有章节对应的 PDF 物理页码范围（`p.X–Y`）、关键数据页码出处及图表位置，全部统一汇总在文件最末尾的折叠块 `> [!note]- 校对报告` 中。

</来源标注与正文零内联页码规则>

<格式与文件命名>

文件开头写 YAML frontmatter：

```yaml
---
title: "短标题或原文主标题"
source: "公众号 / 作者或团队"
date: "YYYY-MM-DD"
type: "技术精读"
tags:
  - 标签1
  - 标签2
status: "待复习"
---
```

- 标题层级使用 `#`、`##`、`###`；代码块之外全篇**严格只设一个一级标题 `# 标题`**，其后依次为 `## 1. TL;DR` 至 `## 10. 原文参考资料`。
- 术语首次出现加粗，保留英文原词；代码、命令、字段用行内代码；公式使用 LaTeX（`$...$` 或 `$$...$$`）。
- 表格、代码块、Mermaid 和 callout 语法保持完整闭合；正文不写「以下是笔记」「我为你整理了」等对话性内容。
- **文件路径与命名**：
  - 在本地微信知识库（如 `/Users/iw/Documents/WeChat_read`）内，严格服从本库目录约定：`公众号/短标题+年.月.日/AI_短标题.md`（与 `META.json` 中的 `files.ai_summary` 一致）。
  - 在知识库之外单独导出单篇文件时，可使用 `{标题} {YY·MM·DD}.md`。

</格式与文件命名>

<校对报告>

文件最末尾必须使用折叠 callout：`> [!note]- 校对报告`，包含以下内容：

1. **页码溯源汇总**：按章节或物理页段（如 `- p.1–3：...`、`- p.4–8：...`）完整列出全文各部分核心内容、图表与关键数值在原 PDF / `MD.md` 中的物理页码出处。
2. **勘误与质量边界说明（如有）**：如实说明原文内部数值矛盾、PDF 文本层公式缺失、右侧代码/命令裁切（未补造）、空白页或实验未独立复现等边界情况。
3. **核验结论**：确认全文单 H1、10 大章节齐全、正文零内联页码、复习闪卡格式合规、数据与原文逐页对齐。未实际渲染或执行过的图与代码，不声称已渲染验证或运行通过。

</校对报告>

<输出>

直接写入目标 `.md` 文件，不在笔记文件内附带额外对话。批量生成任务完成后，在对话中给出包含可点击文件链接的精简汇总表与核验结果。

</输出>
