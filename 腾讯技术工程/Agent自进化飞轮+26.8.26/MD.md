````text
开篇：⼀个被拆散的系统
最近⼏个⽉，我观察到⼀个普遍且致命的现象：评测、记忆、 Self-Improve 这三件事，在⼤

这篇⽂章要做的事是：把这四个环节当作⼀个完整的⼯程系统来讲 —— 它们各⾃的核⼼⽭盾是
什么，应该怎么建设，有哪些坑是前⼈⽤⾎泪验证过必须避开的，最重要的是，它们之间怎么
咬合起来形成⼀个持续转动的飞轮。
你的  Agent 上线半年了。回头看看 —— 它⽐第⼀天聪明了吗？它可能还在犯三个⽉前就
犯过的错。还在重复三个⽉前就⾛过的弯路。还在对三个⽉前就见过的场景表现得像个新
⼿。半年的线上流量喂过去，它⼀点经验都没攒下来。问题不在模型不够强。问题在于
—— 没有⼈给它搭⼀条从 " 做过 " 到 " 记住 " 到 " 变好 " 的路。这篇⽂章基于对  Anthropic 递归
⾃改进报告、斯坦福  CS329A 课程、 EvoAgentX 等开源框架的深度研读，结合业界多个
````

````text
" ⾃进化 " 这个词被⽤得很滥。有⼈拿  Self-Reﬁne （让  Agent 多改⼏版输出）叫⾃进化，有⼈
拿  Agent RL （训模型权重）叫⾃进化。它们是完全不同的东西。
我把它分为三层 ——改什么，就决定了 " 进化 " 的持久性和价值：
第⼀层：Artifacts  迭代 —— 改输出产物。 代码写了三版越来越好、⽅案改了⼏稿越来越靠
谱。但任务结束， Agent 本⾝没有任何改变。下次遇到同类问题，它不会⽐这次更快。这不是
进化，这是打草稿。  这⼀层已经成熟（ Self-Reﬁne 、 Test-time Compute Scaling 等），不是
本⽂讨论的重点。
第⼆层： Harness ⾃改进 —— 改  Agent 的配套系统。  记忆、 Skill ⽂件、 Prompt 、⼯具配
置、⼯作流 —— 这些改动持久化到⽂件或数据库，跨会话⽣效。改⼀次，后续所有任务都受
益。这是当前最具性价⽐的进化⽅向，也是本⽂的主战场。
第三层： Model 进化 —— 改模型参数本⾝。  通过  Agent RL 、⾃对弈微调将经验写⼊权重。持
久性最强，但成本最⾼、风险最⼤。⽬前仍在研究阶段 ——MiniMax M2.7 和业界多个团队
的调研都在探索这条路，但距离⽣产落地还有距离。
为什么  Harness 层是主战场？  四个字：即时、可控。  改完  Skill/Prompt ⽴刻⽣效，不需要
重训模型；改错了⼀键回滚，不会造成不可逆的损害。实测数据也在佐证 —— 已有落地案例通
过  Harness 层进化，迭代次数减少  70% 、 Token 消耗降低  80%+ ；在  Agent Memory 场景中
Token 节省超  60%——这些收益全部来⾃ " 改配套系统 " ，⼀个模型参数都没动。
这三层之间并⾮割裂。 Harness 积累的经验可以变成训练数据改进  Model ；更强的  Model ⼜
能产出更好的  Artifacts 。但在当下这个时间点，Harness 层是投⼊产出⽐最⾼的着⼒点——
接下来四章的讨论都聚焦于此。
⼀个具体的例⼦帮助理解三层的区别：
假设你的 Agent 在处理 " ⽇期格式转换 " 时经常出错。三层分别怎么解决这个问题？
为什么是现在？ 2026 年上半年，⾃进化从 " 学术概念 " 突然变成了 " ⼯程热点 "—— 斯坦福开
了 CS329A 课程、 Anthropic 发布了递归⾃改进报告和 Dreaming 机制、多个开源框架
（ EvoAgentX 等）出现、业界多个团队跑通了完整闭环。这个领域正从 " 能不能做 " 跨越
到 " 怎么做好 " 的阶段。
````

````text
Artifacts 层：让 Agent 在本次任务中多试⼏次、⾃我纠错 —— 这次做对了，但下次遇到同

⽅向指引—— 告诉系统 " 哪⾥有问题 " ，决定进化朝什么⽅向⾛
质量门控—— 更新  Skill/Prompt 前验证 " 改了是否更好 " ，防⽌退化

为什么要强调这三重⾓⾊？因为传统评测只需要承担 " 质量门控 " ⼀个职责—— 上线前跑⼀轮，
达标就放⾏，不达标就打回。但⾃进化场景下，评测多了两个全新⾓⾊：它要告诉系统 " 下⼀

飞轮的第⼀齿。⼀个看不见⾃⼰缺陷的系统，不可能进化。
````

````text
⽤  LLM 给  LLM 打分，听起来很优雅，但评估器⾃⾝可能有系统性偏差 —— 偏好长⽂本（详
细但冗余的答案得⾼分）、偏好特定格式（有编号列表的答案⽐段落式的得⾼分）、偏好表⾯正
确性（引⽤了数据但数据是编造的也得⾼分）。
这种偏差的可怕之处在于：它不是随机噪声，⽽是系统性的。⼀旦评估器有偏好长⽂本的偏
差， Agent 会在多轮进化中 " 学会 " 把答案写得越来越长 —— 不是因为长更好，⽽是因为长能骗
过评估器。错误的正反馈⽐没有反馈更可怕 —— 它让 Agent" ⾃信地学到错误经验 " ，相当于加
速开往悬崖。
难题⼆：评什么维度 ——Agent 的输出不是⼀个单⼀答案。
传统任务评测（如 NLP benchmark ）评的是⼀个答案对不对。但  Agent 的输出是 " 推理过程  +
⼯具调⽤序列  + 中间结果  + 最终答案 " 的组合体。只看最终答案会漏掉⼤量问题：
过程中产⽣了幻觉但碰巧最终答案对了 —— 这种 " 虚假通过 " 下次⼤概率会翻车
⼯具调⽤冗余 —— 做对了但消耗了 5 倍 Token ，效率极低
推理链有错误但因为模型记忆⼒强 " 记住 " 了正确答案 —— 换个问法就垮
只评结果不评过程，盲区⾥的问题永远不会被发现和修复。
难题三：评什么粒度 —— 精度和成本的正⾯博弈。
评 " 整个任务成功 / 失败 " （粗粒度） —— 便宜，但只知道 " 错了 " 不知道 " 错在哪 " 。评测说 "60
分 " ，到底是  Prompt 写得不清楚？ Skill 逻辑有 Bug ？还是 API 调⽤参数根本就写错了？粗粒度
评测⽆法回答这个问题，导致后续修复只能 " 瞎改 " 。
评到 " 每个 step/tool call/ 决策节点 " （细粒度） —— 精确，能定位到具体哪⼀步出了问题，但成
本指数级增长。实测⼀轮完整的细粒度评测需要⼏百到上千次 LLM 调⽤。
粒度的选择直接决定了归因的精度，⽽归因的精度决定了修复能否精准命中。  这⾥没有标准
答案 —— 需要根据场景在两者之间找平衡。我的建议是：⽇常⽤粗粒度做快速筛选，对失败的
case 再⽤细粒度做深度归因。
难题四：开放式任务难量化。
编程任务可以跑测试、 SQL 可以对⽐结果 —— 有确定性的对错标准。但写作、策略规划、⽅案
设计这类任务怎么评？什么叫 " 好的⽅案 " ？⼗个资深⼯程师可能给出⼗个不同的判断。
⼈⼯审查是最终权威，但不可扩展 —— ⼀天审 10 条还⾏，⼀天审 1000 条不现实。纯 LLM
Judge ⼜有上⾯说的弱评估器偏差。这限制了⾃进化在开放式场景的适⽤范围—— 也是为什么
当前最成功的⾃进化案例⼤多出现在编码和确定性任务领域。
对开放式场景的⽅向性建议：⽤偏好排序代替绝对打分（让评估器⽐较 "A 和 B 哪个更好 " ⽽
⾮ "A ⼏分 " ，排序⽐打分更稳定）；或者AI 初筛 + ⼈复核的流⽔线（ AI 先过滤明显不合格的，⼈
只审有争议的 10-20% ）。
````

````text
难题五：评测集漂移 —— 数字漂亮但⽤户骂街。
业务在变、⽤户需求在变、环境在变，但评测集往往半年不更新。 Agent 在旧集上 " 刷出⾼
分 " ，你看着报告觉得⼀切很好 —— 但线上⽤户的真实体验可能在持续下降。
评测集漂移的隐蔽性在于：没⼈会在评测全绿的时候去怀疑评测本⾝有问题。等你发现时，
可能已经在错误⽅向上跑了很远。
难题六：预算公平性 —— 你的 " 进化 " 可能只是多花了钱。
这是⼀个容易被忽视但很深刻的问题。很多 " ⾃动进化 " 的性能提升，可能仅仅来⾃多花了计算
预算 —— ⽐如多次采样然后择优（ Best-of-N ），或者让 Agent 重试⼏次取最好的。这种提升⼀
旦关掉额外预算就打回原形。
真正的进化应该是：在相同的 Token 预算下， Agent 也⽐之前做得更好。  如果新⽅案消耗 3 倍
Token 才⽐旧⽅案好 10%—— 这不是进化，是⽤钱砸分。评估必须在预算对等条件下进⾏，否
则就是⾃欺欺⼈。
难题七：评测成本 —— 每次更新都跑全量评测吃不消。
⼀轮完整评测可能需要⼏百次 LLM 调⽤。如果每次 Skill/Prompt 修改都跑全量 ——Token 成本
很快失控。但不跑⼜怕引⼊回归（原来能做对的做错了）。
这个成本约束直接限制了迭代频率。如果评测太贵导致你⼀周只能跑⼀轮 —— 飞轮就转得很
慢。解法是分层评测：每次改动跑轻量级回归（核⼼ case ），定期跑全量评测（全集）。
1.3 建设要点：怎么搭⼀套可信的评测体系
⼀套完整的评测体系需要回答四个问题：⽤什么⼿段评  →  评测集怎么管理  →  评完怎么处理
结果  →  怎么确保评测器本⾝可信。  下⾯逐⼀展开。
💡  中间⼩结：  前四个难题的共性是 —— 它们都在问 " 评测信号本⾝是否可信 " 。弱评估
器、维度缺失、粒度不对、标准缺失 —— 本质上都是信号质量问题。接下来的三个难题则
是另⼀类问题：信号的新鲜度和成本。
````
