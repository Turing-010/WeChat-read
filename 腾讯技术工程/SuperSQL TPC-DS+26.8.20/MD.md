硬核揭秘⼀：复杂负载下的查询优化
在业界主流数据库系统中，查询优化通常遵循基于规则的优化（ RBO ）与基于代价的优化
（CBO）相结合的标准范式。 RBO 偏向语义层⾯的确定性改写，解决的是局部结构优化问
题；⽽  CBO 则关注全局搜索与资源权衡，基于统计信息和代价模型，在复杂算⼦组合空间
内搜索代价最低的全局最优解。但⾯对复杂多变的真实业务负载，仍存在很⼤局限：
局限⼀：复杂  SQL 中可能存在⼤量语义相同的重复计算，但它们分散在不同⼦查询或算
⼦分⽀中，难以被传统的局部优化规则发现。
局限⼆： Runtime Filter 这类执⾏期动态优化机制的收益与开销往往未被完整纳⼊代价模
型，难以参与全局执⾏计划决策。
局限三：统计信息还可能因为数据倾斜、列间相关性、复杂表达式以及更新不及时⽽产⽣
偏差，并在多层算⼦之间不断累积。
1. AutoCTE ：从局部算⼦优化扩展到全局计算复⽤
在复杂报表、嵌套⼦查询以及⾃动⽣成的  SQL 中，相同或⾼度相似的扫描、过滤、连接和聚
合逻辑经常出现在多个查询分⽀中。现有优化器的优化范围往往受限于显式语法边界，缺乏
从不同⼦查询和算⼦分⽀中⾃动发现复杂公共⼦计划的能⼒。 AutoCTE 通过⾃动识别查询计
划中的重复算⼦⼦树，综合⽐较重复执⾏与公共结果物化、读取和复⽤的成本，选择真正具
有收益的公共⼦计划进⾏抽取和复⽤，在不要求⽤户⼿⼯改写  SQL 的情况下减少冗余计算。
2. Runtime Filter 代价建模：将动态过滤的成本与收益纳⼊全局计划决策
Runtime Filter 通常由  Join 的构建端在执⾏过程中⽣成，并下推到探测端或数据扫描端，以
提前过滤不可能参与连接的数据。它的收益不仅取决于过滤选择率，还受到构建端数据规
模、过滤器⼤⼩以及数据分布⽅式等多种因素影响，⽽过滤器的构建、序列化、传输和探测
本身也会消耗  CPU 、内存和⽹络资源。 SuperSQL 将过滤收益及其⽣成、传输和应⽤成本统
⼀纳⼊代价模型，使优化器能够⽐较启⽤或不启⽤  Runtime Filter 时的端到端执⾏成本，打
通优化器与执⾏层之间的信息壁垒，做出更加符合真实执⾏过程的计划选择。

3. HBO 与  AQE ：利⽤真实执⾏信息修正静态估算误差
