2. LLM 输⼊：上次摘要  + delta →  ⽣成合并摘要

摘要  prompt ⽤结构化输出，四段：进展  / ⽂件  / 待办  / 上下⽂（⽤户偏好、错误、约束）。

6.3 跨轮缓存：让压缩决策在重启后还算数
这是云端特有的问题。

Prompt Cache 全废 —— 消息序列前缀变了，缓存命中率掉到零，每⼀轮都按新  prompt

模型困惑 —— 同⼀段历史在不同轮次⾥ " 长得不⼀样 " ，模型可能重新触发已经处理过的⼯

7. ⼏个关键决策背后的原因
设计过程中有⼏个看似细节但影响很⼤的选择。
为什么阈值是  60 / 80 / 95 ？
60% 是预防性维护的甜点 —— 再低会频繁触发没意义，再⾼模型注意⼒已经开始下降。 80%
是危险线，离溢出还有缓冲但已经不能等。 95% 是最后防线，再不调  LLM 就要爆了。
这三个值都是可配置的常量，接⼊远程配置后能热更新。出问题时把任意⼀个调到  1.0 就能禁
⽤对应  Tier 。
为什么先  Snip 再  Prune ？
Snip 保留更多元信息。⼀个被  snip 的⼯具结果还能让模型看到 " 我之前  grep 过这个⽂件 " ；
被  prune 替换成占位符后连这个都看不到了。 Snip 是轻量记号， Prune 是彻底擦除 —— 能⽤
前者解决的就别上后者。
为什么要增量摘要？
打个⽐⽅：
全量摘要  = 每周把过去三个⽉的⼯作重新写⼀份周报
增量摘要  = 维护⼀份持续更新的项⽬状态，每周只追加和修订变化的部分
哪种更准更便宜？不⾔⾃明。增量摘要还有个隐藏好处：同⼀个⽂件被多次提及时，最新状态
覆盖旧状态；全量摘要⾥这个⽂件可能被描述好⼏次⽽且互相⽭盾。
