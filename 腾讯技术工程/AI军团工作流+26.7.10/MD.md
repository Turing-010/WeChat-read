四、从能跑到可⽤：真实运⾏⾥补出的复杂能⼒
有了  Agent 可调度、⼯作可编排、外部可交接这三根⾻架，系统就具备了跑起来的基础。
但跑起来只是第⼀步。真实场景很快会暴露出  AI ⼯作流和传统⼯作流不⼀样的地⽅： Agent
输出不稳定，复杂⼯作不⼀定是线性的， Agent 完成不等于业务完成，流程可能静默卡住，验
收不通过不能靠⼈重新解释⼀遍，跑完⼀批后还要知道哪⾥应该优化。
下⾯六类能⼒不是为了让系统 “ 看起来 ” 更完整，⽽是真实运⾏中被⼀个个找到的必要能⼒。
4.1 Agent 输出不稳定：准出字段和  Verdict
传统程序节点的输⼊输出通常⽐较稳定，但  Agent 节点不是这样。
它可能输出格式不稳定，漏掉下游需要的信息；也可能⾃然语⾔⾥说了很多，但系统⽆法稳定
消费；它可能失败了但表达得很模糊，也可能  blocked 了但没有形成明确状态。
所以  AI ⼯作流不能假设每个节点天然可靠。我们⽤⼀组结构化字段约束  Agent 输出：业务产
物承载真正要交付的内容，流程裁定（ pass fail blocked ）告诉系统下⼀步该往哪⾥⾛，根因
解释和置信度则把 " 为什么这么判断 " 留在链路⾥，让下游不必重新猜测。
在这套字段之上，每⼀次  Agent 执⾏都会落成⼀次  Submission ，并由系统派⽣出统⼀的
Verdict 状态。下游节点不再去解析⾃然语⾔，⽽是直接消费  Verdict 和准出字段 —— ⽆论这⼀
步交给的是哪⼀个  Agent 。
正向链路跑通只证明 " 能跑 " ，失败路径能处理才证明 " 可⽤ " 。

⼀个需求可能同时涉及前端、后端、配置、模板、测试等多个⽅向。如果仍然让⼀个  Agent
或⼀个节点串⾏做完，效率低，也容易把多个⽅向的上下⽂混在⼀起，导致执⾏结果不稳定。
所以我们补了  Fan-out 并⾏与收敛能⼒。
上游节点可以拆出多个⼦任务，系统根据这些⼦任务动态创建并⾏⼦步骤。每个⼦步骤独⽴⽣
成  Issue / Agent Task ，分配给不同  Agent 执⾏；所有⼦步骤完成后，⽗步骤再  AND 收敛并
推进下⼀节点。⼦任务失败时，可以通过  fail / blocked / rework  等策略决定兄弟任务的命
运。
Fan-out 不是为了并⾏好看，⽽是让复杂⼯作不必被硬塞给⼀个  Agent 。
4.3 Agent 完成不等于业务完成：通知、验收和返⼯
Agent 说 " 做完了 " ，不代表业务真的完成。
业务完成往往还需要负责⼈确认、外部系统验收、发布、 Review 、测试回归或需求⽅确认。
如果把  Agent 完成直接当业务完成，风险很⼤。
所以第⼀阶段增加了  End Node 、完成通知和  Acceptance 机制。
当⼯作流到达结束节点时，系统可以发布完成通知；如果需要验收，则进⼊  Acceptance 状
态。负责⼈可以通过，也可以驳回到指定节点，并带上驳回原因。新⼀轮执⾏会带着  rework
context 重新⽣成任务。
这⾥有两个关键判断。
第⼀，Agent completed 不等于  business completed。执⾏完成和业务完成必须拆开。
第⼆，返⼯应该定向，⽽不是全链路重跑。验收不通过时，应尽量回到真正出问题的节点，并
把驳回原因带⼊新⼀轮执⾏，⽽不是让⼈重新解释⼀遍所有上下⽂。
