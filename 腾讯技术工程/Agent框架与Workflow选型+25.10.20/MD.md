 4.为什么需要使用     Agent框架

结论：只要“问题不可完全穷举、要跨多系统查证、并且需要在对话中澄清/协商/决策”，就更
应该⽤  Agent 框架，⽽不是纯  Workﬂow。

为什么？⽤⼀个真实的     ToC场景客服链                     路来说明。

Workﬂow（⽆论是 Dify 的可视化编排，还是 LangGraph 的状态机）⾮常适合步骤确定 +        条
件有限的流程，⽐如：

2.退货→⽣成标签→发通知

3.FAQ 检索→返回⽚段

⼀旦进⼊长尾问题，    Workﬂow 就会遇     到“分⽀爆炸”：

例：同⼀条“包裹没到”诉求，可能要综合 ①承运商状态 ②发货 SLA ③节假⽇政策 ④地址异
常 ⑤是否会员   ⑥是否已报缺货   ⑦是否已部分签收    ⑧是否叠加优惠券   /补发 等。

如果你⽤固定分⽀描述：

假设有 5 个意图 × 6 种物流状态 × 3 种⽤户等级 × 3 个政策时段（平⽇/⼤促/假期） × 3 种地
理区域，共  5×6×3×3×3=810 条潜在路                径。

这还没算异常（报损、拒收、欺诈信号）与“对话澄清”的分⽀。维护成本和上线速度都会被拖
垮。此外，Workﬂow  对 对话中的“ 澄清—  再决策 — 再⾏动  并不天然友好，需要把每⼀步提
问、回答、重试都画成节点，复杂⽽脆弱。

4.2Agent 框架解决的核⼼问题

以 AutoGen/CrewAI 这类 Agent 框架为例，它们把“在对话⾥动态规划与调⽤⼯具”作为第⼀
性能⼒：

场景： ⽤户说 “我 8 ⽉ 1 号下的单今天还没到                  ，收件地址其实要换，⽽且我被重复扣费了。”

⼀个合格的客服    Agent 团队会做什么             ？

1.意图识别 + 澄清

● Planner Agent：拆出多意图（物流异常、改址、计费异常），先问关键澄清（订单号/新地
址/扣费凭证）             。

2.跨系统取证

● OMS/物流⼯具：查轨迹与    SLA；

● 计费/⽀付⼯具：核对重复扣款交易                                ；

● CRM：看是否  VIP、是否有历史补偿                     记录。

3.政策推理与合规

● Policy/Critic Agent：套⽤“假期延误 + VIP + 改址”的组合条款，评估可给的补偿区间、是否
可免费改址、是否触发风控⼈⼯复核。

4.⽅案⽣成与协商

● 提出“改址 + ⾛加急补发 / 或原包裹拦截 + 退款差额 + 账单冲正”的可⾏⽅案，并在对话中
按⽤户反馈实时调整。

5.执⾏与闭环

● 调⽤⼯单/票据⼯具，落账   /发券/改单/寄件，写⼊   CRM 备注；

● ⽣成总结，告知时限与跟踪号；

● 若任⼀步失败，⾃动选择备选策略或升级⼈⼯。

这些动作⾥，很多步骤⽆法事先“画”成固定分⽀，需要在对话上下⽂⾥做决策、需要跨⼯具动

腾讯云TDAI（TencentDB AI Service，简称TDAI）团队也在积极探索数据库与 AI 的结合，
并正式推出数据库AI服务，为赋予 Agent 长上下⽂理解与个性化交互能⼒，腾讯云在数据库
