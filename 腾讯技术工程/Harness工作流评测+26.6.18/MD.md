2.1 不可量化的东西，不可优化
这是整套系统的第⼀性原理。
传统软件是确定性的：同样的输⼊，同样的输出。你写⼀个asserEqual
它的结果是⼆值的、稳定的、可复现的。
Harness ⼯作流完全不同。它本质上是⼀种" 规则驱动的概率程序 "—— 输出由  Prompt + Rules
+ Skills + Model  共同决定，任何⼀项的微调都可能引起蝴蝶效应般的⾏为变化。今天跑⼀遍
是  A 结果，明天跑⼀遍可能是  B 结果。更要命的是，你甚⾄⽆法简单地判定 "A ⽐  B 好 " 还
是 "B ⽐  A 好 " ，因为 " 好 " 本身就缺乏定义。
这种系统如果没有评测体系兜底，你⾯对的不是 " 缓慢退化 "—— ⽽是薛定谔式的退化：你永
远不知道它什么时候变差了。
2.2 从 “ 测试 ” 到 “ 考试 ” 的思维跃迁
软件⼯程界⽤了⼏⼗年总结出 " 测试驱动开发 " 。但是，传统的单元测试、集成测试那套东⻄
搬到  Harness 上是不够的。
为什么？因为  Harness ⼯作流的 " 正确 " 不是⼀个  boolean—— 它是⼀个光谱。⼀个  Harness ⼯
作流完成任务的⽅式可以有⽆数种，有些优雅有些笨拙，有些主动有些被动，有些严谨有些
草率。你不能简单地  assert output ==  expected
所以我们需要的不是 " 测试 " ，⽽是 " 考试 " ：
测试验证的是 " 对不对 "—— ⼆值判定。
考试评估的是 " 好不好 "—— 多维度打分  + 证据  + 改进建议。
2.3 三个不可妥协的原则
在设计整套系统之前，我们先锚定了三个原则，后来所有的设计决策都围绕它们展开：
可重复  > 精确。  ⼀道题跑多次，结果的分布⽐单次的分数更有价值。我们追求 " 统计显
著的趋势 " ，不是 " 单次满分 " 。
可归因  > ⾼分。  ⼀道题失败了，系统必须能告诉你 " 为什么失败 "—— 是⼯作流规则有漏
洞？是题⽬出得有歧义？还是模型能⼒本身不够？分数不带归因，就是垃圾数据。
闭环  > 单向。  评测的终点不是 " 出⼀份成绩单 " ，⽽是 " 驱动下⼀次改进 " 。如果跑完评测只
能得到⼀个数字，却不知道下⼀步该改什么，那这个数字毫⽆意义。
这个思维跃迁是整套系统的哲学基⽯：我们不是在写测试⽤例，我们是在出考卷、组织
考试、培养阅卷官。

为什么需要考官这个⻆⾊？
这是整套系统⾥最反直觉的设计之⼀。
最朴素的想法是：直接把  task.md 丢给  Agent ，让它跑，跑完看结果。但这完全不符合真实
使⽤场景 —— 真实世界⾥，⽤户和  Agent 之间是多轮交互的。⽤户会追问、会纠偏、会补充
信息、会在关键节点做决策。
如果评测时去掉了这个交互过程，测的就不是 "Agent 在真实场景下的表现 " ，⽽是 "Agent ⾃
嗨的能⼒ " 。两者差距巨⼤。
所以我们引⼊了考官（Examiner ）—— 由  LLM 扮演的 " ⽤户 " ，按照  task.md 中预设的剧本
和  Agent 进⾏多轮对话。
⼀场完整的 " 考试 " 是这样进⾏的
第⼀步：考场布置。  系统根据  env.yaml准备好环境 —— 确认所需⽂件存在、所需服务可达、
⼯作⽬录正确。相当于考试开始前把试卷、答题卡、草稿纸都摆好。
第⼆步：考官开场。  考官拿到task.md  ，理解 " 我要扮演的⽤户⻆⾊ " 和 " 我要提出的需求 " ，然
后向考⽣发出第⼀条消息。这条消息就是⽤户通常会说的那种话 —— ⾃然、简洁、可能还带
点模糊。
第三步：多轮交互。  考⽣（被评测的  Agent ）收到消息后开始⼯作。它可能会：
提问确认细节（ " 你说的服务是  A 还是  B ？ " ）
调⽤⼯具（读⽂件、跑命令、写代码）
汇报进展（ " 第⼀步完成了，接下来我要做  X" ）
请求决策（ " 有两种⽅案，你选哪个？ " ）
考官会根据剧本回应：该确认的确认，该追问的追问，该为难的为难。⽐如剧本可能规
定 " 如果考⽣没有主动确认分⽀名就直接操作，考官要追问⼀句 ' 你确定是在正确的分⽀上
吗？ '" 。
第四步：考⽣完成。  当考⽣认为任务完成时，会给出最终总结。考官确认对话结束。

为什么交互记录如此重要？
这⾥有⼀个关键洞察：Agent 的 " 能⼒ " 不仅体现在最终结果，更体现在过程中的每⼀步决

为什么判卷独⽴于对话？
这是踩过的最痛的⼀个坑。
早期设计⾥，我们让考官 " 顺便 " 判个分。逻辑很⾃然 —— 考官全程参与了对话，它最了解过

结果发现误判率很⾼。

—— 写⽂件、跑命令、调接⼝ —— 这些都发⽣在tool call  ⾥，考官在对话层⾯只看到⼀句 " 我
已完成操作 " 。
于是出现了这种荒谬场景： Agent 明明完美执⾏了所有步骤（从  tool call 记录看），但考官

裁判（ Judge ）是⼀个完全独⽴的进程，与答题对话没有任何共享上下⽂ —— 单独启动、单
