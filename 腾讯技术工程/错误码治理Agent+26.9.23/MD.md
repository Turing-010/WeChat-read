我们基于智能体编排平台搭建了错误码治理 Agent：将知识库、代码关系图谱、可观测平台
数据和代码托管平台四类能⼒挂载到同⼀个 Agent，由它⾃主编排排查流程，分钟级产出根

案例和回归评测持续迭代 Skill。

⼀、从告警搬运到修复建议审核

过去的治理链路是：告警推送给 SRE → 查⽂档、代码和⽇志 → 转给开发 → 开发再次排查
→ 修复。难点不只是告警多，⽽是证据分散，单独查到其中⼀部分仍然⽆法确认根因。

排查瓶颈 需要补⻬的信息

错误码只是⼀个数字 错误码含义、业务规则、服务职责

不知道在哪个仓库抛出 仓库映射、handler、上下游调⽤关系

静态代码不能说明现场情况 错误⽇志、trace、实际耗时与链路

只能转述现象 代码位置、根因分类、可执⾏的修复动作

我们的⽬标是让 Agent 完成根因分析和修复建议，SRE 审核后再推送：high 置信度标注“建

是“这个错误码今天出现了 X 次”，⽽是带证据和代码位置的排查结论。

让 SRE 从“告警搬运⼯”升级为“修复建议审核员”。

### 3.2 交叉验证：代码怎么写，不等于现场怎么跑

假设静态代码显示 A 调⽤ B，只有结合 trace 才能区分：是 A 内部多次串⾏调⽤导致累积超
时，还是请求到达 B 后由 B 报错。两种情况对应的责任点和修复动作完全不同。

前后端也需要相互验证：后端错误要检查前端调⽤⽅式和错误处理，前端错误要核对后端返
回结构。前端源码没有获取到，就明确说明，不能凭后端代码推断；⼊⼝函数将错误处理委
托给其他函数时，还要继续追查，不能停在⼊⼝。

### 3.3 置信度模型

### 五、⽤真实 case 调优，⽽不是不断堆规则

基于优化前 v3 与优化后 v4 的 50 条 case 对⽐，我们进⾏了 5 轮 Prompt 调优。除前⽂的
检索路径、调⽤预算和输出契约外，改动重点是判定顺序与修复建议边界。

### 5.1 先排除，再判断是否加⽩

“加⽩”指将错误码加⼊告警豁免清单，不再触发告警推送。

v3 将“加⽩条件”和“不能加⽩场景”并列陈述，Agent 容易先匹配更宽松的加⽩条件。v4 改
为显式三步：先检查禁⽌加⽩场景，全部排除后再判断加⽩条件，最后区分 whitelist 与
whitelist\_and\_refine。

关键规则包括：限流类错误优先判为 rate\_limit\_internal/external；兜底通⽤码先
fix\_code 细化，不能直接 whitelist\_and\_refine；超时优先排查代码和配置，只有云资源本
身故障且代码配置⽆法优化时，才选择 handle\_cloud\_resource。若语义明确属于预期业务
拦截，则结合业务规则判断，不能只看 code\_type。

### 5.2 修复建议要有边界

Agent 容易倾向“多给建议”：给每个调⽤点加 if-else、修改不会触发问题的⼊⼝、为低频偶
发问题扩展错误码体系。我们补充三条原则：只修改实际触发问题的⼊⼝；优先复⽤已有集
中处理表或中间件；新增错误码和抽象层前先评估⽤户处理差异与 ROI。

### 6.2 上线运⾏与协作变化

⼯作流已在智能体编排平台上线，近⼀个⽉内⽇均处理数百条去重错误码告警，覆盖后端与
