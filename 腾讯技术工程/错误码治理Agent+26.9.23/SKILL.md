## 1. 错误码治理Skill说明节选

### Skill原文

````text
Agent 收到  error_context  后，以五步流程组织排查，并根据已有结果决定具体查询路
径：
1. 补全错误码语义。
  输⼊的  gcode_meaning  为空时，⾄少⽤两种⽅式复核，包括⽂档、代码定义或运⾏时⽇
志；查不到则填  ErrUnknown_<retcode>。
2. 建⽴业务上下⽂。
  检索前后端仓库映射、业务架构、 API ⽂档和历史经验，为代码定位提供起点。
3. 定位代码与调⽤链。
  定位  handler ，拉取源码，追查上下游和错误码定义，遵守上⼀节的检索路径与调⽤预算。
4. 采集运⾏时证据。
 查询⽇志及  tag 分布，检索  trace 和完整链路，必要时补充前端洞⻅。
5. 补充最近变更。
 已定位到具体代码⾏时，按需查询  blame 和  commit ，填充  recent_change。
每条  evidence 标明来源，如 “ 知识库命中 ”“ 代码关系图谱  context”“ 可观测平台  log”“ 可观
测平台  trace”“ 代码托管平台  blame” ，⽅便⼈⼯回查。
3.2 交叉验证：代码怎么写，不等于现场怎么跑
假设静态代码显示  A 调⽤  B ，只有结合  trace 才能区分：是  A 内部多次串⾏调⽤导致累积超
时，还是请求到达  B 后由  B 报错。两种情况对应的责任点和修复动作完全不同。
前后端也需要相互验证：后端错误要检查前端调⽤⽅式和错误处理，前端错误要核对后端返
回结构。前端源码没有获取到，就明确说明，不能凭后端代码推断；⼊⼝函数将错误处理委
托给其他函数时，还要继续追查，不能停在⼊⼝。
3.3 置信度模型
当前模型将知识库、代码定位、实际源码、运⾏时证据各计  1 分： 3 ～ 4 分为  high ， 2 分为
medium ， 0 ～ 1 分为  low 。若错误码含义⽆法补全，置信度最⾼为  medium 。
代码托管平台变更信息不计分：知道谁改了代码，不能直接推出根因；可观测平台的⽇志和
trace 则⽤于验证运⾏时情况，参与评分。分级结果⽤于第⼀节的⼈机协作与推送策略。
````

### 使用步骤

1. 准备error_context和业务知识、代码图谱、日志／trace访问条件。
2. 按原文五步收集证据，交叉检查静态代码和运行现场。
3. 按证据充分性分级，并由人工核对根因与动作建议。

### 预期输出

可回查的错误码语义、代码位置、根因证据、置信度及修复建议。
