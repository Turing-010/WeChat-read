本次是在苹果发布最新iOS 26 系统的背景下，Kuikly新增全新“液态玻璃”适配，进⼀步丰富平
台特性⽀持、助⼒业务体验提升。



 ⼀、引⾔

在今年的 WWDC25 上，苹果发布了其近⼗多年来最重要的⼀次视觉设计⾰新 —— 液态玻璃
（Liquid Glass）。这种全新的设计语⾔，以其半透明3D质感和动态流体效果，为⽤户创造了
前所未有的沉浸式体验，也让软件与硬件的界限变得更加模糊。

“液态玻璃”的出现，将⼀个跨端开发领域中长期存在的根本性问题，以⼀种前所未有的⽅式重
新推回到了聚光灯下：⼀个跨端框架，应该如何处理与宿主系统之间的关系？

这背后是两种截然不同的架构路线：

● ⾃绘渲染（Self-Rendering）：追求在所有平台上提供像素级⼀致的体验，通过⾃带的渲染
引擎在系统画布上绘制所有   UI，从⽽实现最⼤程度的控制⼒和跨平台⼀致性。

● 原⽣渲染（Native-Rendering）：致⼒于将框架的抽象层⽆缝对接到原⽣系统的UI组件和渲
染管线上，以最⼤化地利⽤平台特性、保证性能和跟进系统级的创新。

过去，关于这两种路线的讨论更多集中在性能和⼀致性的权衡上。⽽“液态玻璃”的出现，则将
“ 跟进平台创新的能⼒ ”这⼀维度，提升到了⼀个新的⾼度。本⽂将基于这⼀背景，分析“液态
玻璃”对跨端开发的影响，并结合 Kuikly 在“原⽣渲染”路线上的探索与实践，分享我们的经验
与思考。

 ⼆、什么是   “液态玻璃”？

“液态玻璃”是苹果继 iOS 7 的扁平化之后，在 UI 设计上的⼀次重要演进，它标志着UI设计正
从“扁平化”向“沉浸化”过渡，其核⼼在于对光学、材质和纵深感的全新探索。

从苹果给我们的解读看，这⼀设计的核⼼特征主要体现在两⽅⾯：

● 光学特性与动态流动性：“液态玻璃”能实时根据背景内容和环境光线进⾏“折射”和“反射”，
使UI元素的颜⾊和光泽随上下⽂动态变化。

## PDF物理页 3

● 多层级界⾯结构：   通过将 UI分为背景、内容和悬浮的互动层，创造出显著的空间感与深
度。

这些特征已在最新的iOS 26系统中得到⼴泛应⽤。例如，App图标现在由多层玻璃构成，可动
态适应主题⾊；  Safari的悬浮⼯具条在                                滚动时也会⾃动收缩，以保证内容的全屏呈现。

但与以往的风格迭代不同，“液态玻璃”的实现并⾮纯粹的视觉技巧，⽽是深度依赖于系统底层
的图形处理能⼒。它不再像传统设计那样模拟纸张、油墨等物理隐喻，⽽是通过调⽤硬件加速
的渲染管线来直接创造光线与材质的交互效果。

这种变化意味着，UI效果的实现⽅式发⽣了根本改变：从软件层⾯的“模拟”，转向了对底层硬
件能⼒的 “直接调⽤ ” 。⽽这⼀转变，也给现有的跨端框架带来了新的技术                                                                                                                      挑战。



 三、不同架构路线的适配分析

“液态玻璃”的推出，对应⽤开发者提出了新的要求。随着⽤户逐渐习惯系统级应⽤所提供的流
畅、灵动的“液态玻璃”视觉效果，未适配的应⽤在体验上可能会出现割裂感。因此，如何有效
跟进这⼀设计趋势，成为开发者需要考量的问题。

⾯对这⼀变化，基于不同架构路线的跨端框架，其适配路径和成本也表现出显著差异。

3.1⾃绘渲染路线

对于采⽤⾃绘渲染路线的框架（如      CMP 、Flutter）⽽⾔，其核⼼特点是在系统提供的画布
上，通过⾃带的渲染引擎（如 Skia）绘制全部 UI。这种架构在保证跨平台视觉⼀致性上具备
优势，但在适配  “液态玻璃 ”这类深度依赖原⽣系统的特性时，则⾯临着独特                                                      的挑战。

因为 “液态玻璃 ”并⾮简单的视觉滤镜，⽽是与系统渲染器（Metal         ）及核⼼动画（Core
Animation）深度绑定的硬件加速效果，⾃绘框架⽆法直接调⽤系统 API 来实现。其适配路径
通常是通过⾃定义着⾊器（Shaders）或图像处理技术，在⾃⾝渲染引擎内对原⽣效果进⾏视
觉上的模拟。这种模拟不仅成本⾼，结果也往往不尽⼈意：性能和保真度较低，视觉效果难以

完全对齐原⽣。更重要的是，这种架构上的不匹配会成为长期问题。未来任何依赖系统级深
度、光线或动态效果的更新，⾃绘框架都将再次⾯临被动的     “模拟”难题。

正如Flutter社区中部分开发者所⾔：“重新实现各种设计语⾔的成本和难度正变得越来越⾼。”
这体现了⾃绘渲染路线在设计理念上的核⼼取舍：优先保障跨平台视觉的绝对⼀致性，相应
地，在跟进特定平台的深度创新时则需要付出更⾼的⼯程成本。

3.2 原⽣渲染路线

与⾃绘路线不同，以Kuikly、Hippy、ReactNative等为代表的“原⽣渲染”框架，在适配平台级
创新时则更具天然优势。这类框架通过将上层抽象映射为原⽣      UI 组件来进⾏渲染。

这种架构使得它们能够直接利⽤和封装系统发布的新特性。当苹果推出“液态玻璃”时，原⽣渲
染框架可以通过调⽤系统提供的原⽣    API，让框架内的组件直接获得新效果的加持。

这⼀路径的优势在于：

● 较低的适配成本：⽆需从零模拟，主要⼯作在于对原⽣ API 的封装和框架层⾯的暴露，开发
成本相对较低。

● 较⾼的保真度：由于直接使⽤系统能⼒，最终呈现的效果在视觉和性能上能与原⽣应⽤保持
⼀致。

● 可持续的演进能⼒：框架的设计理念决定了它能与宿主系统的创新保持同步。未来的平台级
更新，同样可以通过相似的路径被快速集成。

对于 Kuikly ⽽⾔，原⽣渲染的价值不⽌于 UI 呈现。更重要的是，这种架构选择确保了框架能
够与宿主平台的技术演进保持同步，使得基于 Kuikly 的应⽤能够持续、低成本地集成系统级
创新，给⽤户带来与系统原⽣应⽤相同的优质体验。



 四、Kuikly的适配经验

作为致⼒于提供⾼性能、原⽣   UI渲染的跨端框架，Kuikly现已完成对“液态玻璃”的⾸阶段适
配，并对外开源发布。Kuikly的适配⼯作并⾮简单的UI改造，⽽是充分利⽤原⽣提供的基础能
⼒，在框架渲染层和DSL驱动层两⽅⾯进⾏扩展，旨在为开发者提供⼀套便捷、低成本的适配
⽅案。

4.1 适配原则

Kuikly框架在适配“液态玻璃”时，需要平衡⼀个核⼼问题：如何在保持我们“通过Kotlin跨端层
组合原⼦组件以最⼤化UI⼀致性”的核⼼理念，与“液态玻璃”所强调的平台原⽣特⾊之间做出
选择。⾯对这⼀挑战，我们选择灵活处理：将⽤户体验置于最⾼优先级，在追求⼀致性的同
时，积极拥抱平台特⾊。

我们认为，跨端⼀致性的重点，是在不同平台提供符合⽤户习惯的优质体验，⽽不是追求UI像
素的绝对相同。因此，我们选择以⼀种灵活、务实的⽅式来拥抱平台特⾊。对于常⽤组件，尽
可能在跨端层抹平差异，提供⼀致的开发体验；同时通过“⾃定义组件”来解决系统对⾼级组件
所做的特殊优化，例如叠加的复杂交互动画效果。这种设计思路，使得我们能够在统⼀代码库
的基础上，仍能充分发挥平台原⽣体验的优势。

4.2 开发者友好的API设计

Kuikly在API设计上同样追求简洁与⾼效。对于常⽤的View、Button等组件，为了适配“液态玻
璃”，我们没有引⼊新的独⽴组件，⽽是为现有组件提供了简洁的视图属性扩展。例如，开发
者只需通过⼀⾏  glassEﬀectIOS() 代码，即可为任意容器视图启⽤液态玻璃效果。

4.4 兼容性保障

在适配新特性的同时，   Kuikly也全⾯考量了兼容性问题：

● 对旧系统的兼容：对于使⽤了液态玻璃的组件，Kuikly封装的系统原⽣组件会⾃动处理兼容
性，在旧系统上平滑切换为原有样式。⽽对于组合类组件，框架也提供了兼容性保障，业务代
码⽆需担忧在旧系统上出现异常。

● 对其他平台的兼容：对于使⽤了液态玻璃的代码，Kuikly框架保障在Android      等不⽀持的平
台上能够⾃动降级到默认实现，避免业务UI代码编写⼤量的平台判断逻辑 。利⽤这⼀机制，
开发者可以在iOS上采⽤最新设计语⾔，同时⽆需为其他平台维护⼀套独⽴的UI，极⼤地降低
了开发和维护成本。

 五、总结与展望

“液态玻璃”的出现，为我们提供了⼀个绝佳的案例，去重新审视跨端框架的两种核⼼路径：是
“抽象并抹平平台差异   ”，还是“集成并利⽤平台能⼒    ”？

过去，跨平台开发的核⼼挑战是保证体验的⼀致性。但随着操作系统能⼒的不断发展——从空
间计算（AR/VR）到硬件加速的AI能⼒——“抽象”的成本，可能正在变为错失平台最有价值的
创新。 ⼀个框架的价值，不再仅取决于它能      “抹平”什么，更在于它能   “释放”什么。
