⾯对这种两难，传统路径给出的答案往往是放弃技术：许多技术管理者最终转型为纯粹的"职

### 3. ⼤模型推理⼯程⼊门指引

⼤模型推理⼯程是⼀项涉及模型结构、GPU 底层硬件特性、分布式系统与调度的复杂系统⼯
程。它不是单纯的深度学习模型部署，核⼼⽭盾是算⼒、显存、通信三者之间的权衡：Prefill
阶段是计算密集型，Decode 阶段是显存带宽密集型；KV Cache 、Continuous Batch、
Prefix Cache、TP 等技术，本质上都是为了在硬件约束下，以最低成本换取更⾼的吞吐与更
低的时延。

知识点覆盖⾯较⼴，建议采⽤先总后分的思路：先建⽴体系化认知，再逐个击破。

### 3.2 对⼤模型推理⼯程建⽴体系化认知

在分析技术问题时，⽆论是单个模块还是完整领域，⾸要⼯作是明确两个问题：要解决什么问
题，有什么评估体系。掌握了核⼼⽬标和评估体系，对系统中每个组件就会有更本质的判断：
该组件如何⽀撑整体⽬标，以及如何量化它的优劣。

⼤模型推理⼯程的顶层⽬标与传统软件⼯程⼀致，包含功能、性能、成本、稳定性等维度。⽽
评估体系包含以下核⼼指标：TTFT 、TPOT、QPS、TPS、Concurrency（并发数），还有成
本。围绕这些指标，在系统层⾯做的每⼀项优化，都可以归纳为算⼒、显存、通信三者之间的
资源置换。据此，我们可以抽象出三层模型：顶层是业务⽬标，中间层是量化评估标准，底层
是具体实现⼿段。

落到⼯程体系与组织分⼯上，上述"实现⼿段"可进⼀步划分为三个⼦⽅向：

业务层：负责推理系统与上层业务的对接。包含推理服务 SDK、推理平台、服务部署与监
控、⾯向业务定制的请求流量调度等模块。

调度层：作为模型推理运⾏时载体，直接决定系统核⼼性能，绝⼤多数推理加速优化都落
地于此层。典型技术包括分布式并⾏、Prefix Cache、Overlap Scheduler、Continuous
Batch、Chunked Prefill、Speculative Decoding 等。

算⼦层：负责⾼性能基础计算单元的实现，聚焦单点计算性能优化，例如 QKV 计算、
Normalize、Linear 计算。

分层架构的核⼼价值，是降低⼤规模系统与⼤型研发团队的复杂度，让各⽅向的团队聚焦⾃⾝
职责边界。⽽对于业务规模较⼩、系统复杂度偏低的场景，则不必做如此精细的切分，研发⼈
员可以跨多个层次开展⼯作。

同样可以借助 AI 学习，建⽴⼀些基础概念。对于有开发经验的程序员来说，形成体系化的认
知是⽐较简单的，难的是深⼊细节，譬如 Prefix Cache、Overlap Scheduler 是怎么实现的。

### 3.3 了解主流模型结构的演进趋势

在⼤模型时代，传统的“算法”与“⼯程”岗位边界⽇益模糊。对于推理⼯程⽽⾔，只懂系统架构
已远远不够，深⼊理解模型结构同样是必修课——因为新⼀代模型结构的演进，本质上是算法
创新与⼯程优化深度结合的结果。从最初的 Full Attention + Dense FFN，发展到如今的稀疏
注意⼒、线性注意⼒、混合架构、MoE，以及 Pre-Norm、RoPE、MLA、KV Cache 跨层复⽤
等技术，仔细梳理这条演变路径不难发现：模型在变得更智能的同时，也在朝着⼤幅降低计算
复杂度、更适配长上下⽂的⽅向演进，以更低的推理成本实现更⾼的吞吐。DeepSeek 就是这
⽅⾯的典型代表：注意⼒层的 MLA、HCA、CSA 等设计，以及 DSpark 推测解码，都是算法
创新与⼯程优化结合的案例。

进⼀步思索，会发现现阶段⼤模型的结构演进，本质上是⼀门“实验科学”。很多创新都是可想
到的，当创新点⼦变得廉价，昂贵的就是验证思路的实验是否可以更好更快的完成。这时候
infra 显然极其重要，理解模型结构，搞明⽩演进背后的动机，可以帮助我们理清趋势，进⽽
做出更完备、更有前瞻性的 infra。

### 3.4 深⼊某个优化⽅向

⼤模型推理⼯程涉及的知识体系极其庞杂。在建⽴起宏观的体系化认知之后，建议结合具体的
业务痛点或个⼈兴趣，选定⼀个细分的主题进⾏分析学习。⽬前来看，投⼊产出⽐较⾼且业界
⾼度关注的⼦⽅向包括：

Prefill / Decode（PD）分离：通过将 Prefill 与 Decode 阶段解耦部署，能显著提升整机
吞吐与资源利⽤率，对于算⼒预算有限、卡资源紧缺的团队⽽⾔尤为关键。尽管开源已经
有⽐较好的实现，但是结合⾃⾝的业务场景，怎么适配到性能最佳，也很有挑战。

分布式 KV Cache：针对具备多轮交互、长上下⽂特点的业务场景，能够⼤幅提升 Prefix
Cache 的命中率，显著降低重复计算成本。

推测解码（Speculative Decoding）：作为算法创新与⼯程优化深度结合的典范（例如
DSpark 等架构），它巧妙利⽤了 Decode 阶段算⼒未饱和的特点，⼤幅度提升系统吞吐。

除了这些⼤⽅向，还有很多有趣且独⽴的"⼩技术点"值得深挖。例如我此前曾对 Overlap
Scheduler 做过系统分析《 ⼤模型推理加速：Overlap Scheduling 的深⼊剖析与性能权衡艺
》。当顺着底层执⾏链路深挖下去时，往往能发现⼀些被常⼈忽略的暗礁，譬如在特定约束
术
下，Overlap Scheduler 反⽽可能会破坏 Continuous Batch 的批处理效率。这种对微观机制
的钻研可以通过 Demo 代码完成验证，学习沉淀也会更加扎实。

### 4.1 同批次共享前缀的注意⼒优化

估⽂档。

将该问题抽象出来，本质就是：同⼀ Batch 内的共享前缀的注意⼒计算优化。要完整解答并

### 4.2 Beam Search 的⼯程实现

Beam Search 技术最近⼀两年在搜⼴推领域较为⽕热，这与快⼿发布的 OneRec 论⽂
（OneRec Technical Report）密切相关，不少公司也已经将这项技术落地到内部的搜索、推荐
项⽬中。

Beam Search 的技术原理较为简单直接：每⼀步在 backbone 和 LM Head 执⾏完后，挑选
token 时不再只保留最优的⼀个，⽽是保留多个候选 token，作为多条⼦路径继续推导；每⼀
步选择下⼀个 token 时，将多条⼦路径的候选汇总到⼀起，按整条⼦路径累积的对数概率
（logprob）排序，保留得分最⾼的 Beam Width 条继续推导，如此迭代，直到⽣成结束后选
出最佳⼦路径。

来的多个⼦请求，需要理解推理引擎的 KV Cache 实现，然后做到⾼效的复⽤；

### 5.1 传统 Infra 知识体系依然是⼤模型推理服务底座

今天我们对外提供⼤模型推理 API 服务，其底层依然搭建在传统 Infra 能⼒之上：微服务、分

### 5.3 传统后台开发的价值重估与 Agent Infra 新战场

### 5.3.1 传统⼯程经验在 AI 时代更显重要

当下 AI Infra 领域的招聘⽅普遍偏好有训推框架、内核算⼦开发等经验的 AI Native ⼈才，但
我认为传统后台⼯程师的转型价值被低估。AI 专项⼈才虽可以更快上⼿，但传统⼯程师凭借
扎实的系统设计功底，依托 AI ⼯具辅助，也可以很快追上，并发挥⾃⾝的经验优势。

AI 普及替代了基础编码等重复⼯作，让代码评审、架构设计成为核⼼事项。传统⼯程师长期
积累的代码品味、架构思维与复杂系统把控能⼒，在 AI 时代愈发重要，可以有效规避 AI ⽣成
代码的架构混乱、冗余与隐性风险。

由此我判断，在当前 AI Infra ⼈才稀缺的情形下，让有热情的后台开发⼯程师扩展知识边界，
进⼊到 AI Infra 领域，在团队管理和⼈才培养上都是不错的选择。

### 5.3.2 技术⽅向的分层需求：越往底层需求越少、越往上层需求越多

AI Infra ⾏业具备清晰的分层特征：越底层共性越强、需求越少，越上层业务差异化越⼤、⼈
⼒需求越旺盛，整体呈现"底层标准化、上层差异化"的格局。以⼤模型推理⼯程为例，各层级
需求特征如下：

算⼦层：模型结构、硬件⽣态将趋于收敛，新算⼦、新结构适配类似 Linux 内核迭代，核
⼼价值极⾼、全⾏业可复⽤，但⽆需⼤量⼈⼒重复研发，仅需少量头部团队持续迭代适配
新模型、新硬件即可，整体⼈⼒需求极少。

推理引擎调度层：通⽤调度能⼒已被开源⽣态成熟覆盖，绝⼤多数业务⽆需深度定制，仅
少数业务绑定的场景存在少量定制需求，整体⼈⼒需求有限。

业务层：⾃⾝业务场景的定制适配、链路优化、稳定性打磨等差异化⼯作，是⼈⼒需求⽐
较⼤的地⽅。

业务层的差异化⼯作，正是传统后台⼯程师迁移系统设计功底、发挥经验优势的主战场。
