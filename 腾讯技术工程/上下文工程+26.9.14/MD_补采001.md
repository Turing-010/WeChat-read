2. 什么是  Context Engineering
2.1 Anthropic 的核⼼定义
“Context engineering is the art and science of curating what will go into the limited context
window from that constantly evolving universe of possible information.”
—— Anthropic, Eﬀective Context Engineering for AI Agents, Sep 2025
这个定义字字有深意，拆开来看有三个关键词：
▸  关键词⼀：策展（ Curating ）
“策展 ” 意味着主动选择和剪裁，⽽不是被动堆砌。就像⼀位博物馆策展⼈，不会把仓库⾥所有
的⽂物都摆出来 —— 他会精选那些能讲好故事的展品。 Context Engineering 要求⼯程师像策
展⼈⼀样，主动决定哪些信息进⼊上下⽂、以何种形式进⼊、放在什么位置。
▸  关键词⼆：最优（ Optimal ）
“ 最优 ” 不是 “ 最多 ” ，⽽是 “ 信噪⽐最⾼ ” 。最优的  Token 集合是：以最少的  Token 数量，传递最
关键的信息，使模型能做出最准确的下⼀步决策。加⼊⼀个⽆关的  1000 Token ⽂档，可能反
⽽会降低模型的表现 —— 因为它稀释了真正有⽤信息的信号。

7.2 ReAct 的四⼤上下⽂陷阱
随着  TAO 循环不断累积， ReAct Agent 会落⼊四个典型的上下⽂陷阱，这是导致 “Agent ⽤久
了越来越差 ” 的根本原因。
▸  陷阱⼀： Observation ⽆限膨胀
每次  Action 调⽤⼯具后， Observation 被永久追加到历史⾥。即使  Agent 早已 “ 消化 ” 了信息
并做出决策，原始的⼯具返回值仍然占据上下⽂空间。⼀个  50 轮任务，仅  Observation 累计
可超过  80,000 Token ，其中⼤部分对当前决策毫⽆价值。
▸  陷阱⼆：规则漂移（ Rule Drift ）
这是最隐蔽也最危险的陷阱。系统指令在任务开始时位于上下⽂开头，模型能清晰看见；但随
着  TAO 循环推进，对话历史快速增长，系统指令被从 “ 开头 ” 推⼊了 “ 中间 ”—— 正好落⼊  Lost
in the Middle 研究发现的 “ 性能洼地 ” 。这个现象在实践中表现为： Agent 在前  10 轮严格遵守
命名规范，从第  20 轮开始偶尔出错，到第  30 轮已经完全混⽤不同风格。⼯程师往往把这归
因为 “ 模型不稳定 ” ，实际上是规则漂移导致的。
▸  陷阱三：错误轨迹污染（ Error Contamination ）
⼯具调⽤失败、 API 超时、格式解析错误是常态。 ReAct 的容错机制会让  Agent 在  Thought
⾥记录失败然后重试，但这些失败的  Thought 和错误的  Observation 都被永久保留在上下⽂
历史⾥。⼀旦⼀条错误信息进⼊上下⽂，它就会影响后续所有轮次的推理，就像⼀个 “ 谣⾔ ” 在
系统⾥流传，越传越影响模型的判断 —— 这是  Context Rot 的⼀种具体表现形式。
▸  陷阱四： Thought 冗余积累
ReAct 的每⼀轮  Thought 都被完整保留在历史⾥。这些中间推理在当时很有意义，但随着任
务推进变成了纯粹的历史记录，不再提供信息价值，却持续消耗  Token 预算。以⼀个  40 轮任
务为例，仅  Thought 部分累计约  8,000 Token ，其中真正对当前决策有价值的可能不超过最近
3 ～ 5 轮。

9. 常见误区与反模式
掌握了  Context Engineering 的正确做法，同样重要的是了解常见的错误做法。以下是⼯程实
践中最频繁出现的五⼤反模式。
▸  反模式  1 ： “ 更多上下⽂更安全 ” 的幻觉
表现：把所有可能相关的⽂档、所有历史对话、所有⼯具调⽤记录都保留在上下⽂⾥， “ 万⼀
⽤到了呢？ ” 问题：这是  Context Rot 和  Attention Budget 约束最常见的触发⽅式，⽆关内容
稀释关键信息，上下⽂越长，模型对早期关键指令的遵从度越低。
⚠  原则  最优的上下⽂不是最长的上下⽂，⽽是信噪⽐最⾼的上下⽂。
▸  反模式  2 ：⼯具越多越好
表现：注册了⼗⼏个⼯具，覆盖所有可能的操作场景。问题：⼯具定义本⾝消耗  Token ；更重
要的是，功能重叠的⼯具会让  LLM 产⽣决策困惑，⼯具选择错误率上升， Agent ⾏为变得不
可预测。
⚠  原则 ⼯具集应该 “ 够⽤ ” ⽽不是 “ 全⾯ ” 。每个⼯具有清晰的职责边界，功能不重叠。
▸  反模式  3 ： System Prompt 越详细越可靠
表现：在系统提⽰⾥列出所有可能的边缘情况和对应处理规则，⼏千字的系统提⽰覆盖每⼀种
可能场景。问题：过度细化（违反  Goldilocks Zone 原则）会导致  Token 浪费（⼤多数规则⽤
不到）和脆性（遇到未枚举场景时不知如何处理）。
⚠  原则  系统提⽰应该提供 “ 原则 ” ⽽⾮ “ 枚举 ” 。让  LLM 根据原则推理，⽽不是查表匹配规则。
▸  反模式  4 ：不清理⼯具调⽤结果
表现：⼯具调⽤的完整原始结果永久保留在对话历史中，不做清理。问题：⼯具调⽤结果可能
⾮常长（⼀次⽂件读取可能  3000+ Token ），当任务继续推进，这些早期结果已经不再需要，
但仍占据⼤量上下⽂空间，加速  Context Rot 。

▸  场景⼀：智能客服  Agent （多轮对话）
核⼼挑战：客服对话轮次多，⽤户可能在同⼀会话内问多个不同问题，上下⽂混乱会导致
Agent “ 记混 ” 不同问题。
1. Instructions ：明确⾓⾊边界，⾼风险操作（退款、注销）列明需要升级⼈⼯的原则
2. State/History 管理：采⽤滑动窗⼝（保留最近  8 轮） + 关键信息外部笔记（⽤户诉求、情
绪状态）；环境状态只注⼊⽤户等级、订单  ID 等关键字段，不注⼊完整档案
3. Tools ：明确区分 “ 查询类⼯具 ” 和 “ 操作类⼯具 ” ，操作类⼯具调⽤必须有确认步骤
▸  场景⼆： AI Coding Agent （长期开发任务）
核⼼挑战：代码审查 / 重构任务轮次极多，⼯具调⽤返回结果量⼤， Context Rot 是最主要的质
量杀⼿。
1. Instructions ： Goldilocks Zone 原则，提供编码规范和⼯具使⽤原则，不枚举所有场景
2. Long-Term Memory （ Skills ）：把经过验证的重构步骤、审查  Checklist 封装成  Skill ，按需
调⽤
3. State/History ：激进的  Compaction 策略（ 60% 阈值触发），⼯具调⽤结果读完即清除；
只维护 “ 当前审查的⽂件清单 ” 和 “ 已完成清单 ” ，不注⼊完整⽬录树
4. 外部笔记：严格执⾏  Structured Note-Taking ，所有重要发现实时写⼊
▸  场景三：复杂研究报告  Agent （多路信息融合）
核⼼挑战：需要同时从多条信息路径获取信息并综合出有深度的报告，单个  Agent ⽆法维持
所有路径的深度探索。
1. 架构：采⽤  Sub-Agent Architecture ，主  Agent 负责规划和综合，⼦  Agent 负责各路径深
度探索
2. 主  Agent 的上下⽂：只包含任务⽬标  + ⼦  Agent 返回的精炼摘要（每路  1000 ～ 2000
Token ）
3. 检索策略： JIT 检索，每个⼦  Agent 只检索⾃⼰负责的那条路线的相关⽂档

随着  Gemini 1.5 Pro 的  100 万  Token 窗⼝和各家模型不断扩展的上下⽂能⼒，⼀个⾃然的问
题是：窗⼝越来越⼤， Context Engineering 还有必要吗？
“ 上下⽂窗⼝变⼤，并不会使  Context Engineering 变得不重要，⽽是将挑战从 “ 如何装下⾜够
信息 ” 转向 “ 如何在百万  Token 中组织最优的信息结构 ” 。 ”
—— Anthropic Engineering Team, 2025
Context Rot 在⼤窗⼝⾥同样存在： 100 万  Token 的窗⼝⾥， 1 万  Token 的关键指令同样

Attention Budget 代价更⾼： O(n²) 的注意⼒计算，在百万  Token 窗⼝⾥意味着更长的延
迟和更⾼的成本。
