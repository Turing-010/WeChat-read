2.2 第⼀个坑：⽤传统软件设计思维来设计  Agent 体系
第⼀篇⽂章发出时，我⼿⾥已经有了第⼀版  demo—— 基于第⼀篇的认知搭建的初始⼯程。接
下来的迭代过程中，我本能地⽤了最熟悉的设计⽅法：领域驱动设计（ DDD ）。 第⼆篇⽂章正
是在这段迭代中写的 —— 它记录了我们如何从三层架构、九步⼯作流、多  Agent 编排的 " 精密
设计 " 中清醒过来，受  NotebookLM 和  Claude Code 的极简理念启发，推翻全部架构，回归
到 " ⼀个  AGENTS.md + 结构化知识 " 的起点。
这个思路很⾃然 ——DDD 是应对复杂业务系统的成熟⽅法论：划分限界上下⽂、定义聚合
根、设计领域事件、通过接⼝契约解耦模块。既然  Agentic Engineering 也是⼀个复杂系统，
为什么不能⽤  DDD 来设计它？
从  v0.1 到  v0.7 ，我反复尝试⽤  DDD 的⽅式划分  Agent 的职责边界、定义  Skill 之间的调⽤契
约、设计知识的分层架构。每⼀版都⽐上⼀版 " 更完整 " ，但每⼀版在实际使⽤中都不对劲 ——
Agent 不按你设计的边界⾏动。
最终才意识到根本性差异：传统代码写了就确定性运⾏， Agent 的⾏为取决于上下⽂。
⽤  DDD 设计微服务时，你可以精确定义⼀个接⼝：输⼊什么类型、输出什么类型、异常怎么
处理。写完代码，部署上去，它就按你定义的⽅式运⾏。但  Agent 不是这样 —— 同⼀个
Skill ，给它完整的项⽬知识，它能⼀次做对；给它空的  context/ ，它就开始幻觉。同⼀个
Agent 定义，上下⽂窗⼝⾥塞了太多规则，它反⽽ " ⾛神 " ；精简到关键信息，它⼜表现正常。
Agent 的 " 接⼝ " 不是函数签名，⽽是上下⽂窗⼝⾥的信息组合。这个 " 接⼝ " 是动态的、概率性
的，没法⽤  DDD 的确定性边界去约束。
v0.7 之后我放弃了  DDD 路径，推翻之前的设计，建了当前这个全新的仓库。这个认知直接影
响了后续所有的设计决策：不追求精确的模块划分和接⼝定义，⽽是围绕上下⽂的组织、流转
和质量来构建体系—— 这就是第三章开始的故事。
这个认知断层还延伸出两个⼯程化问题，最终都指向了同⼀个答案。
问题⼀：体系怎么升级？
传统⼯具的升级路径是 " 发布新版本→⽤户更新插件 " 。但  Agentic Engineering 的核⼼资产是
什么？ Skill 定义、 Agent 配置、 context/ ⾥的知识、门禁规则 —— 全是⽂本⽂件。升级⼀个
Skill 的⾏为，本质上是修改⼀个  Markdown ⽂件；调整⼀条门禁规则，本质上是编辑⼀个
JSON 。
这意味着  git 就是天然的升级机制。git pull  完成升级，git diff  看到每⼀⾏变化，git merg
e 处理冲突。不需要版本号、不需要发布流程、不需要兼容性矩阵。当体系的核⼼资产是⽂

功能预期是否更新了？设计追溯表的正向和反向索引是否同步了？场景规范是否补充了？⼯具

10.1 Token 消耗量正在成为衡量团队⽣产⼒的新指标

个错误反复付费修正。它的  token 利⽤率很低。

消耗），⼯具化的约束让  Agent 调⽤即合规（减少⼈⼯纠偏的  token 消耗），渐进式披露让
Agent 只加载需要的信息（减少上下⽂浪费的  token 消耗）。
