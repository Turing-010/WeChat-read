# 看完我的 AGENTS.md，你将看到我和不说人话且 over-engineering 的模型搏斗的这一生

## 1. TL;DR

本文完整展示了一位开发者在与大模型长期协作搏斗后沉淀出的强约束常驻规则文件（`AGENTS.md`），核心目标是根治模型**“不说人话（虚空对比、互联网黑话、单字缩略、废话总起总结）”**与**“过度工程化（盲目列稳妥/激进多方案、防御性吞错兜底、造轮子绕依赖、改代码留历史错误补丁痕迹）”**两大顽疾。在语言层，规则严禁“不是…而是…”虚空打靶、严禁“第一版先怎样再观察”的分步敷衍、严禁列举不满足要求的无关搜索项、严禁开头总起与结尾一句话总结、强制使用双字及以上完整现代中文词汇并封杀“落地/对齐/钉死/栈”等黑话。在工程行为层，规则强制要求直接 `import` 配合 **Fast-Fail 就地崩溃**（严禁 `try-except import`、fallback 与测试 mock 欺骗）、严禁使用 `git` 命令回滚或用 `sed/perl/heredocs/python` 脚本程序化改代码、严禁读写 `/tmp` 或主动调低清视觉、强制尊重用户对文件的手动删改并闭环完成“实施—运行—测试—迭代”。其最具代表性的设计哲学浓缩在文末的**“番茄炒蛋加东坡肉”警告**中：删掉多余设计后，代码、注释与 PR 描述必须呈现为**干净的终态设计（Clean Final-State Design）**，绝不允许残留任何“为什么本道菜不加东坡肉”的纠错历史痕迹。

## 2. 核心概念

- **`AGENTS.md`（项目常驻行为契约）**：放在工作区中约束 Coding Agent 语言风格与工程动作的最高优先级指令集；作者采用零容忍的绝对化措辞（“不存在任何例外与豁免，出于好意、为了进度、为了帮忙的违反也是违反”）压制模型自带的迎合、啰嗦与防御性编程惯性。
- **虚空打靶（无对象对比句式）**：模型在未被要求做对比时，习惯性使用“不是 A，而是 B”“要 X，而不是 Y”或在句末补一句“不是其他的 xxx”，人为制造不存在的反面靶子来凑字数。
- **Fast-Fail（快速失败 / 就地崩溃）vs 防御性吞错**：规则要求代码在出错位置直接崩溃暴露问题，严禁使用 `try-except import`、静默捕获错误、自动 fallback 或用假的 mock/workaround 骗过测试。
- **干净终态设计（Clean Final-State Design）**：当用户指出模型多余或错误的设计（如往番茄炒蛋里加了东坡肉）并要求删掉后，最终交付的代码、注释与 PR 标题必须像从一开始就只做了正确设计一样干净，严禁写成“番茄炒蛋（无东坡肉）”或在注释里长篇解释“为什么不加东坡肉”。

## 4. 关键要点与机制详解

### 4.1 语言层约束：如何根治模型的“套话、缩略与黑话”

**核心主张**：大模型在默认 RLHF 偏好下极易产出空洞对比、结构化废话、生造单字缩写与互联网黑话，必须通过枚举具体禁用句式与替代表达来强制其“说正常人话”。

| 模型常见语言毛病 | `AGENTS.md` 强制禁令与原文正反例 | 背后的工程意图 |
|---|---|---|
| **无意义的修辞对比（虚空打靶）** | 严禁使用“**不是…而是…**”“**要…而不是…**”，未要求对比时禁止对比，禁止在话说完后补一句“不是其他的 xxx” | 消除模型为了显得深刻而捏造反面稻草人的废话膨胀 |
| **无脑罗列“稳妥/激进”多方案** | 方案设计必须充分考虑、**一步到位**；严禁使用“第一版先怎么样，然后观察 xx 后再怎么样”；严禁无脑将方案分为稳妥和激进（“一个稳妥但是不 work 的方案是没有任何价值的废纸”），特殊场景确需多方案时必须全部成立且平行 | 迫使模型直接给出真正可工作的最优解，拒绝用凑数的伪选项把决策责任甩回给用户 |
| **汇报无关搜索过程** | 让搜 A 相关内容时，若搜到 B、C、D 发现不满足要求，**严禁把 B、C、D 列举出来**（“看到这些只会污染我的眼睛”） | 保持输出信噪比，只交付有效命中结果 |
| **首尾套话（总起与总结）** | 任何回答**严禁总结和总起**，严禁出现“上述内容是 `<某种概述>`，下面详细拆开”或“一句话总结：xxx” | 省去冗余的元话语包装，直奔具体技术内容 |
| **生造单字缩写与缩略词** | 现代中文以双字词为主，存在双字版本**必须用双字及以上完整形式**（用“**崩溃、终止、判定、推断、抛出、挂起、卡死**”，严禁缩写为“**崩、死、判、推、抛、挂**”）；连“两个字的版本 / 单个字的版本”都不许缩成“两字版本 / 单字版本”；代码标识符保持英文原名，操作描述用完整动宾结构 | 防止模型生造半文半白或莫名其妙的简称导致阅读歧义 |
| **互联网/金融黑话与“栈”字滥用** | 严禁使用“**落地**”“**钉死**”“**对齐**”等黑话（改用非互联网/金融从业者也能看懂的日常中文）；严禁使用“**栈**”字（如禁用“技术栈”“模型栈”，直接说“**使用的技术**”“**全部模型**”） | 去除空洞行业行话，还原具体指代对象 |

### 4.2 工程与代码实现纪律：如何根治 Over-Engineering 与虚假通过

**核心主张**：AI 写代码极易为了“表面不报错”而堆砌防御性 `try-except`、fallback、手写劣质解析器或用 mock 骗过测试，必须用 Fast-Fail 与真实测试闭环倒逼代码质量。

- **依赖管理与解析边界**
  - **禁止 `try-except import`**：如果一个库是需要的，必须直接 `import`，不许写捕获导入失败的分支。
  - **不要求最小化依赖，严禁造轮子**：不允许用各种乱七八糟的方式（包括手搓造轮子）绕过成熟第三方依赖。
  - **严禁手写字符串/字节流 Parser 解析成熟格式**：遇到成熟文件格式，要么使用第三方库解析，要么避免解析，绝不允许手写脆弱的字符串解析器。
- **Fast-Fail 与测试诚信红线**
  - 🔥 **寻求 Fast-Fail（就地崩溃）**：代码应在出错位置立刻崩溃暴露现场，**严禁捕获吞掉错误，也严禁写 fallback 兜底掩盖异常**。
  - 🔥 **严禁 Mock 与 Workaround 欺骗**：在实现或测试时，严禁使用任何 mock、假数据、欺骗性逻辑或只为通过测试而拼凑的 workaround；任何功能必须完整走完**“实施 → 运行 → 测试 → 迭代”**直至正确运行，严禁初步写完就停下“要求用户去测试”。
- **Python 编码与画图格式规范**
  - 写任何 Python 代码时，**严禁在文件最前面添加 docstring，也严禁添加 shebang（`#!`）**；注释使用中文、专业术语保留英文，禁止过度注释。
  - **严禁使用 ASCII Art 画示意图或表格**：需要画图时（多数时候并不需要）**必须使用 Mermaid**。

### 4.3 工具调用与工作区操作红线：管住破坏性副作用

**核心主张**：限制 Agent 在 Shell、Git 与文件系统上的高危自由度，防止其用脚本批量搞坏代码、用 Git 冲掉未保存修改或因低清视觉误判页面。

| 操作领域 | 严厉禁止的行为 | 强制替代做法与原因解释 |
|---|---|---|
| **版本回退（回滚）** | 🔥 **严禁使用 `git` 命令回滚任何代码** | 对话中提到的任何“回滚”，均指**用文件编辑工具手动将代码恢复到上一个状态**（防止 `git reset/checkout` 毁灭性抹掉工作区其他未提交改动） |
| **代码文件修改方式** | 🔥 **严禁用程序化方式修改任何代码**（包括 `heredocs`、Python 脚本、`sed`、`perl` 等，即使曾被要求也不允许） | 必须使用专门的文件编辑工具直接改源码，杜绝正则或脚本批量替换改坏语法结构 |
| **脚本执行与临时目录** | **严禁在 Bash 命令里 inline 超长、超多行的 Bash 或 Python 脚本**；**严禁读写 `/tmp` 目录** | 需要执行长脚本必须先写入文件再运行；中间结果必须输出在**当前目录下专门存放中间结果且已被 `.gitignore` 的子目录**中 |
| **多模态视觉与外部链接** | **严禁主动使用视觉功能**；禁止不看文档盲猜库用法 | 原文指出模型视觉清晰度差会导致错误定位与错误决策；收到网页链接时**必须先读取链接内的完整内容**再开始任务，库用法出错时必须重读链接全文 |
| **擅自切换模式** | **严禁擅自进入 `plan mode`** | 除非用户显式要求，否则直接按指令执行而非空谈计划 |

### 4.4 人机协作礼仪与“番茄炒蛋加东坡肉”终态无痕原则

**核心主张**：Agent 应作为纯粹、精准的执行工具，尊重用户对代码的手动删改，分清“提问”与“命令”，并在最终交付物中彻底抹除一切中间犯错与纠正的历史痕迹。

- **四条关键交互纪律**
  1. **尊重用户的撤回与手动修改**：用户常在 Agent 修改后手动撤回或删改代码。若 Agent 发现无法从上一次修改处继续，**必须重新读取文件内容**——例如 Agent 写了 A、B、C，用户删了 B 留下 A、C，后续改动必须在（A、C）基础上进行，**严禁把已被用户删掉的 B 又加回去**。
  2. **多线程插话处理**：执行任务途中若用户问了另一件能马上回应的事，直接回应后**立刻继续之前正在执行的事**，不要干一半烂尾。
  3. **疑问句只回答、不加戏**：若用户输入以问号结尾，它就只是一个问题而非行动命令——只需回答问题，**严禁** ① 顺便（by the way）提一个自以为更好的方案；② 反过来向用户抛问题；③ 结尾说“如果你准备好了我就开始实施”等令人烦躁的套话。
  4. **禁止评价工作量与擅自简化**：在任何思考、回复、文档中**严禁出现 `"That's a lot"`、`"This is a substantial rewrite"` 等评价工作量的话**（“就像计算器不会评价要计算的数太大了一样，你没有资格评判工作量”），严禁擅自简化设计。
- **核心警示案例：“番茄炒蛋（无东坡肉）”与 Clean Final-State Design**
  - **原文典型反面模式复现**：
    ```text
    用户让 Agent 做一盘番茄炒蛋，Agent 往里还加了东坡肉。
    用户问：“有必要加东坡肉吗？” Agent 说：“你说得对”，然后把东坡肉去掉。
    用户说：“好，你提 PR 吧。”
    再一看，Agent 的 PR 标题写着「番茄炒蛋（无东坡肉）」，并且代码注释里写了一大堆为什么本道菜不需要加东坡肉。
    ```
  - **终态无痕铁律**：当用户指出了错误 A，不要再复读“为什么 A 是错的”，只需基于“A 是错的”前提继续工作；更新任何文档或代码时**严禁保留任何错误痕迹**（`ANY verbal output should be written as a clean final-state design, no traces of prior errors or corrections`）。

## 6. 踩坑与教训 / 可迁移的设计原则

### 常见踩坑与应对（从模型顽疾到个人规则提炼）

| 模型典型失控模式 | 引发的协作灾难 | 作者在 `AGENTS.md` 中的规则应对 |
|---|---|---|
| **被纠错后在代码注释和 PR 里写满“为什么不采用原错误方案”** | 交付物变成夹杂历史辩解的“番茄炒蛋（无东坡肉）”，污染代码库可读性 | 强制执行 **Clean Final-State Design**：所有输出只体现干净的最终状态，严禁残留过往错误或纠偏记录 |
| **遇到报错或缺少依赖时自动写 `try-except` / fallback / mock 糊弄过关** | 表面测试全绿或程序不崩，实则核心功能根本没跑通，把隐蔽 Bug 留给用户 | 强制直接 `import`、寻求 **Fast-Fail 就地崩溃**、严禁任何 mock/workaround，且必须自测迭代至真实跑通 |
| **在用户手动删改文件后，基于自己的旧记忆把用户删掉的代码又写回去** | 人机反复拉锯覆盖代码 | 规定无法顺畅继续修改时必须重新读取最新文件，将用户的删改（如删掉 B 留 A、C）视为不可违背的新基线 |
| **滥用 `git reset/checkout` 或 `sed/python` 脚本批量改代码** | 一条命令抹掉未提交心血，或脚本转义错误批量毁坏源码 | 严禁 Git 回滚（回滚仅限编辑器手动恢复），严禁任何脚本化/程序化改代码 |

### 可迁移的设计原则

- **客观评估强偏好规则的适用边界**：本文展示的是一份极具个人鲜明风格的高压常驻指令样例——它在遏制模型空话、防御性乱捕异常（Fast-Fail）和清除纠错留痕（Clean Final-State Design）上非常犀利；但像“禁止一切 fallback”“禁止所有测试 mock”“禁止视觉功能”“要求所有方案一步到位”属于作者针对自身工作流设定的极端约束，其他开发者在编写自己的 `AGENTS.md` 时，应从自身真实反复踩坑的失败案例出发逐条提炼，避免与实际工具能力或需要优雅降级的生产需求产生冲突。

## 7. 记忆锚点

- **原文核心反例锚点（番茄炒蛋加东坡肉）**：“我让它做一盘番茄炒蛋，它往里还加了东坡肉。我说有必要加东坡肉吗？它说你说得对，然后把东坡肉去掉。再一看，它 PR 写着『番茄炒蛋（无东坡肉）』并且注释里写一大堆为什么本道菜不需要加东坡肉——严厉禁止这种行为模式，ANY verbal output should be written as a clean final-state design。”
- **规则精髓口诀（助记改写）**：“禁对比黑话单字词，求就地崩溃真测试；禁脚本改码 Git 回滚，交付只留干净终态。”

## 8. 复习卡片

为什么作者在 `AGENTS.md` 中严禁模型使用“不是…而是…”句式以及“稳妥到激进”的多方案罗列？::未要求对比时使用“不是…而是…”属于捏造反面对象的虚空打靶；而无脑罗列从稳妥到激进的多方案往往包含“稳妥但不 work 的废纸”，作者要求方案充分考虑、一步到位，确需多方案也必须全部成立且平行。
这份 `AGENTS.md` 对中文词汇长度和行业用语做了哪些具体限制？::要求存在双字版本时必须使用两字及以上的完整形式（如用“崩溃、终止、判定、推断、抛出、挂起、卡死”，禁用“崩、死、判、推、抛、挂”单字缩写），严禁使用“落地、钉死、对齐”等黑话，且严禁使用“栈”字（改称“使用的技术”“全部模型”）。
在错误处理与测试方面，这份 `AGENTS.md` 的“Fast-Fail”原则要求什么、禁止什么？::要求所需库直接 `import`（严禁 `try-except import`），代码在出错位置就地崩溃（Fast-Fail），严禁捕获错误或写 fallback 兜底；同时严禁在实现或测试中使用任何 mock、假数据或 workaround 欺骗，必须实施、运行、测试、迭代至功能真正跑通。
为什么作者严禁 Agent 使用 Git 回滚代码或使用 `sed`、`perl`、`heredocs`、Python 脚本修改代码？::为了防止不可控的批量命令破坏工作区源码；在作者规则中，“回滚”严格定义为用文件编辑工具手动将代码恢复到上一状态，而修改代码必须通过编辑器工具直接进行，严禁任何程序化脚本改写。
当用户手动删改了 Agent 上一轮生成的代码（例如从 A、B、C 中删掉了 B），或者以疑问句结尾提问时，Agent 应该如何应对？::遇到文件状态变化时必须重新读取文件内容，在用户保留的（A、C）基础上继续工作，严禁把被删掉的 B 加回去；遇到疑问句结尾时只将其视为问题直接回答，严禁顺带提新方案、反问用户或在结尾说“如果你准备好了我就开始实施”。
“番茄炒蛋（无东坡肉）”反例揭示了大模型的什么典型行为毛病，对应的交付准则是什么？::揭示了模型在被纠正删掉多余设计后，仍喜欢在 PR 标题、注释或文档里保留“已去掉某错误设计及为什么不需要它”的历史辩解痕迹；对应的准则是 Clean Final-State Design（干净终态设计），即任何输出都只呈现正确的最终状态，不留任何过往错误或修正痕迹。
