## 先理解这个问题

Skill 解决的是“某类任务应该怎样做、需要哪些知识和资源”，其价值来自可复用的判断与步骤。一个名字、一份提示词、一个脚本、一个插件包分别可能参与实现，却不能凭名称判断能力。尤其要分清：**能发现、会触发、能执行、做得正确、具有权限**是五件事。

本专题把 Skill 看作有输入、条件、产物、失败分支和验证依据的任务知识包。稳定、完全确定的转换可以交给程序；业务语义和例外留给模型或人判断。不要把所有对话规则都复制进技能，也不要将文章中的命令当成本库安装授权。（art-0217，p.1—10；art-0089，p.1—4、8—16）

## 共同机制与最小例子

### 发现与执行分两层测试

名称和 description 帮助宿主判断何时载入；正文描述如何做；细节文件按需加载。应同时准备应触发、不应触发和边界任务，检查路由；再用真实输入检查产物和失败处理。只对“已经命中该 Skill”的调用评分，会漏掉漏触发和误触发。提示词变长、提醒更强硬都不证明遵从率提高。（art-0027，p.1—12；art-0103，p.7—8、27—36；art-0217，p.7—10）

**最小教学例子：订单导出技能。** 发现层写清“导出指定条件的订单明细”，排除“查询订单统计口径”和“创建订单”。执行层先确认日期、对象、字段和权限；脚本分页取数并对账总数；输出文件、行数、筛选条件和失败列表。对“导出昨天订单”测正确触发，对“解释订单数为何下降”测不误触发；对分页中断、空结果、字段变更测执行。文件非空只证明有产物，不能证明全量或准确。

### 渐进披露是内容加载，不是按标题自动省 Token

合理入口指向唯一规则源，让团队、项目、端类型和任务各读必要内容。单个 SKILL.md 里用标题和决策树拆分路径可以改善理解，但宿主若整篇载入，仍会消耗整篇上下文；只有将低频细节外置并实际按需读，才改变加载量。元数据也有成本，不能说“未命中零成本”。百补详情助手把稳定本地协议与变化快的远端分析分开，是部署与维护边界的选择，额外网络和协议版本也带来成本。（art-0039，p.4—11；art-0191，p.1—10；art-0210，p.2—7）

### 文字规则、程序门禁和服务端权限各有职责

Skill 可说明必须检查，Hook 可在某个时点注入提示或阻断调用，脚本可验证结构与退出码，业务服务可执行对象级授权。必须检查实际实现，不能因文件叫 Hook 就认为不可绕过。输出枚举合法不说明业务含义正确；脚本始终退出0还会把失败伪装成成功。所有等效写入路径都要落实同一权限与状态约束。（art-0057，p.18—19；art-0089，p.8—16；art-0103，p.15—18、33—40）

### 技能更新是一种工程变更

记录来源、适用项目和依赖版本；从已验证任务提炼经验，用新任务测试，再发布和回滚。应把内容效果、路由效果、费用和安全分别观测。企业购案例以真实错误定位 Skill、修改约束、回归并交叉验证；定位服务迁移先读二方包源码，再写映射，避免用常识猜内部 API。将这些文件更新称为“训练技能”是日常比喻，不能推断模型权重已更新。（art-0215，p.16—21；art-0216，p.1—10；art-0067，p.5—11）

## 当前适用性核查（2026-10-23）

[Agent Skills 开放规范](https://agentskills.io/specification)当前要求目录至少包含 SKILL.md，name/description 是必要元数据，scripts、references、assets 为可选；按发现、正文、资源渐进加载。主文件行数和 Token 数是组织建议，不是固定换算。allowed-tools 为实验字段，支持依宿主而异；agents/openai.yaml 等产品文件不是该开放规范的通用必需项。格式通过只能证明约定满足，不能证明脚本、权限或业务效果。

[MCP 当前授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)定义 HTTP 传输授权；STDIO 使用不同凭据路径。Skill 方法、MCP 连接、宿主许可和业务对象授权应分别核对。本轮只核官方格式和职责，未安装文章提供的技能，也未把版本相关命令变成现行操作手册。

## 边界与待验证项

AB 分析技能必须核对随机化单位、重复用户、统计目标与指标口径；非正态不能机械推导为改用 Mann–Whitney，Bonferroni 也不能解决反复偷看结果。数值上升不能直接推出上线决策。（art-0212，p.5—6、12—16）

“门禁”需明确阻断位置、失败状态和绕过路径。“AI每次都执行”“结构100%正确”“7倍效率”等来源结论保留案例范围；正例和反例测试只覆盖实际样本。技能升级还需考虑旧包、宿主快照和运行会话的不同生命周期；重启是否刷新旧会话应按具体版本核实。（art-0063，p.9—13；art-0191，p.7—8）

## 自测：先回答，再展开

<details><summary>1. 单个 Skill 分成五个标题，为什么可能完全没有减少输入 Token？</summary>

宿主可能一次载入完整文件。标题优化逻辑组织；物理外置和按需读取才改变实际加载量，还要计入常驻元数据。
</details>

<details><summary>2. 10个命中任务全成功，能否说明触发可靠？</summary>

不能。需要独立的应触发、不应触发和边界任务，统计漏触发与误触发；命中后的执行成功是另一层指标。
</details>

<details><summary>3. Hook 注入“先检查权限”是否已实现权限门禁？</summary>

没有。要看执行端是否使用可信身份、参数与目标验证并在失败时阻断，且所有等效调用路径都受控。
</details>

<details><summary>4. 技能包静态检查通过，又有成功案例，还需验证什么？</summary>

固定包版本和依赖在目标环境运行未见任务，核产物真实性、失败分支、权限和成本。精选案例不能估计真实失败率。
</details>

<details><summary>5. 如何把一次失败经验变成可复用规则？</summary>

保留原问题、已证根因、修复证据与适用版本；归纳条件和反例；独立回归验证再发布，记录失效与回滚路径。
</details>
